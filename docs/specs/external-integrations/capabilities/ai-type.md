# "AI provider" type: pluggable AI backends (implemented)

Goal (community RFC, topic 10421): let external integrations provide the **AI backend** of the assistant — Claude, DeepSeek, OpenAI, Mistral, a local LLM… — instead of Gladys Plus. Gladys Plus remains the default for every connected user; switching to an external provider is an **explicit administrator choice**, per instance.

This file has no historic section identifier (the README's rule: none is allocated to a new file) — it is cited by its path, `capabilities/ai-type.md`.

**Why a type and not a capability field.** `capabilities/provider-type.md` sets the bar for a new `type`: *a generic pivot interface the core itself consumes (dashboard, assistant, scenes), never a domain*. `ai` passes it the way `weather` and `calendar` did: the pivot is the **OpenAI-compatible chat completion** — one request format, one completion format — and the core consumes it on its own through a single provider resolution (`gateway.aiChat`) for everything that asks an AI: the chat tool-calling loop, the intent router, the scene `ai.ask` action and the weekly digest. The integration renders nothing, evaluates nothing and calls no tool: it answers completions. The type also carries what a field could not: a screen set without Devices/Discovery, an admin-only selection gesture, and the highest trust class an integration can hold (below).

**The contract is provider-agnostic by construction.** Verified in the code: the whole agentic loop — MCP tool calling, intent router, system prompts, conversation history, image resizing — runs **on the Gladys instance** (`gateway.forwardMessageToAiChat`), and the only thing that leaves is `gateway.aiChat(body)`: an **OpenAI-compatible chat completion request** (`messages`, `tools`, `tool_choice`, `max_tokens`, plus the Gladys hints `purpose` and `categories`), answered by an OpenAI-compatible completion (`choices[0].message` with `content` / `tool_calls`). That format is the de facto industry standard — every major provider either speaks it natively or is a mechanical translation away (Anthropic, Gemini…). The core therefore knows **no provider**: the external integration is a thin adapter that receives the request, calls whatever API it wants with whatever SDK it wants, and returns a completion.

## Design

- **Manifest**: `type: "ai"` (C.1, `contracts/manifest.md`). No type-specific manifest field: everything provider-specific — API key, endpoint URL, model choice, temperature, context window… — lives in the integration's own `config_schema`; the core never validates nor understands those values. `messaging` / `contact_schema` stay refused outside the communication type, every other field (`containers`, `actions`, `webhooks`, `categories`…) keeps its own rules whatever the type.
- **Screens**: Configuration / Supervision / Logs only — `ai` joins `TYPES_WITHOUT_DEVICE_SCREENS` (the shared frontend list), so its catalog card, its post-install redirect (store, GitHub and dev installs alike) and its direct URLs land on the configuration screen of the shared external integration page. No device surface: an AI provider never goes through discovered devices or states. **The configuration screen carries the next step**: installing an AI provider is not enough, an administrator has to select it — the screen opens with a card saying whether this integration is the assistant's AI provider ("active", linking to the AI settings) or not yet ("installed but unused", with a **Use as AI provider** button that performs the selection right there and a link to the AI settings) — the card says it is checking until the selection is read and, when the read fails, says so with a retry rather than "unused"; the install warning names the two places where the selection happens.
- **Catalog**: **admin-only**, hidden from non-admins like `device`, `weather` and `provider` (there is no per-user block: the provider serves the whole instance). Browse placement comes from `categories` (`integration-catalog-categories.md` §2.2), the display axis decoupled from `type`: an AI provider declares `assistants`, the shelf of the native AI page and of MCP.
- **Proxy service capability `ai.chat(request)`** (the B.15 extension pattern: `device.*`, `message.*`, `weather.*`, now `ai.*`), attached to the proxy of every `type: "ai"` integration and to no other: relay over WS `external-integration.ai.chat` with the standard `command-result` ack carrying the completion in `data` (contract below). Ack deadline **120 s** (a documented exception to the 5 s rule, like `camera.get-image` and the per-action timeouts): reasoning models are slow, and one request can carry a full tool-calling context. **Exception within the exception: `purpose: "intent-classification"` gets 20 s** (`AI_CHAT_INTENT_CLASSIFICATION_TIMEOUT_MS`) — the router runs before every chat turn, swallows its own failures (the loop then falls back to all tools) and asks a short prompt; a stuck provider must fail it fast instead of putting two full deadlines in front of the user.
- **The completion is never trusted** (the B.18 doctrine, transposed): its content drives the tool-calling loop **with the user's authority** (device control, scene creation), so the supervisor **bounds** it before it enters the loop — only `choices[0].message` is kept, with `role: "assistant"`, `content` (a string capped at 50 000 characters, or `null`) and `tool_calls` (≤ 20 entries, each reduced to `id` (≤ 128 chars, `null` when absent), `type: "function"`, `function.name` matching `^[a-zA-Z0-9_-]{1,64}$` and `function.arguments` a string ≤ 100 000 characters, `"{}"` when absent); every other field (`usage`, `model`, `finish_reason`, extra choices, unknown keys) is dropped. Anything else — no object `choices[0].message`, a non-string `content`, a tool call the loop could not run — fails at the contract boundary with `ExternalIntegrationUnavailableError('EXTERNAL_INTEGRATION_INVALID_AI_RESPONSE')`, surfaced as the "provider unavailable" reply below, never a crash and never a silent empty turn: adapter bugs surface as an explicit invalid-response error. The bounds are the constants `MAX_AI_CHAT_CONTENT_CHARS`, `MAX_AI_CHAT_TOOL_CALLS`, `MAX_AI_CHAT_TOOL_ARGUMENTS_CHARS` and `AI_CHAT_TOOL_NAME_REGEX` of `server/lib/external-integration/constants.js`.
- **Concurrency cap**: at most **4 requests in flight** per AI integration (`MAX_AI_CHAT_IN_FLIGHT`); beyond it a request fails at once with `EXTERNAL_INTEGRATION_AI_PROVIDER_BUSY` (the "provider busy" reply below) instead of queueing behind the others until the ack deadline — an `ai.ask` scene fired on every motion cannot flood a CPU-bound local model. The slot is released when the relay settles (ack, failure or timeout). The weekly digest asks for **one admin at a time** so digest requests never compete with each other, whatever the number of administrators (a digest can still overlap with a chat turn: it takes one slot like any request).
- **Selection: one provider per instance, stored in the system variable `AI_PROVIDER`** (absent = Gladys Plus). Admin gesture from the AI settings page (the `openai` integration page): a select listing Gladys Plus plus every installed `type: "ai"` integration (`GET /api/v1/ai_provider`, below), restating the trust warning once a provider is selected (with a positive line naming the provider the assistant now uses) and warning when the selected provider is not running; two installed providers sharing a display name are told apart by their selector in the select. Setting it validates that the selector is an installed `ai` integration and re-checks the row after the write (a provider uninstalled concurrently is rolled back to the default); **uninstalling the selected provider clears the variable** — read after the row deletion, so a selection written while the uninstall runs is caught too, and the two re-checks cover both interleavings (return to the Gladys Plus default — no dangling selector; the uninstall confirmation of the active provider says so, since with a Plus account the conversations then go to Plus again — the confirmation re-reads the selection when it opens, since it can change while the page is open, says it is checking until the answer comes back, and when that read fails says it could not check rather than staying silent; the value is a selector string, never a foreign key, and a stale value reads as "provider not available" below, repaired by reselecting). Selection is deliberately not a lock-protected transaction: both gestures are admin-only on a single-process server and the failure mode is explicit and recoverable.
- **Routing**: `gateway.aiChat` is the single funnel of all AI traffic — the selected provider therefore serves **all** of it (chat loop, intent router, `ai.ask`, weekly digest), not just the chat. The external branch sits **before** the Gladys Plus plan gate (`callPlanGatedApi`): an instance whose Plus subscription is paused keeps using its own provider, never a 402. The `model` field is **stripped** before the relay: model ids are Gladys Plus (Scaleway) vocabulary, meaningless elsewhere — an external provider chooses its model in its own config (the frontend hides the per-message model selector when an external provider is active). The `purpose` hint passes through — `chat`, `intent-classification` or `weekly-digest` (`AI_CHAT_PURPOSES` of `server/utils/constants.js`) — with the intent `categories` of the chat requests: generic hints that let a smart adapter pick a cheap model for the router and a strong one for scene creation, exactly like the Plus gateway does.
- **No silent fallback (privacy rule)**: a stopped, broken, disconnected or busy provider fails the request and is **never** silently rerouted to Gladys Plus. The failure is **named, not a generic "try again"**: the chat loop answers `openai.provider-unavailable` (stopped, disconnected, ack timeout, invalid completion or a stale selection — "check it on its integration page or switch back to Gladys Plus in the AI settings") or `openai.provider-busy` (the in-flight cap), two brain answers in every brain language, where a Gladys Plus failure keeps the historical `openai.request.fail`. Choosing an external provider can be a privacy decision ("my conversations only go to X"): Gladys does not send them elsewhere because X is down. The selection card says so.
- **AI without Gladys Plus**: `message.create` engages the AI path when Gladys Plus is configured **or** an external provider is selected — an instance with no Plus account gets the full assistant through its provider. Neither → the "Gladys Plus required" reply, as before. The **weekly digest** gates the same way: with an external provider it needs neither a Plus account nor an active subscription (delivery goes through the instance's own channels). The AI settings page, the scene `ai.ask` editor and the chat follow: the Plus upsell, the rate-limit note and the Plus quota are not shown while an external provider is active, the digest settings and the debug context download are offered to administrators as soon as the assistant has a backend, Plus or external (their routes are admin-only). The copy follows too: the AI page intro and the `ai.ask` action description name the selected provider instead of Gladys Plus, the empty chat no longer upsells Plus, and a non-admin sees on the AI page which provider the conversations go to.
- **Scene `ai.ask` on a failed request** (a fix that predates the type but matters more with local models): the chat loop resolves `null` when the request failed (provider down, ack timeout, no usable answer) and the user already got the failure reply; the action then aborts the scene with the explicit reason `AI_REQUEST_FAILED` instead of running the following actions on an undefined answer.
- **The raw completion proxy is an admin tool**: `POST /api/v1/gateway/aichat/chat` (the replay path of the debug context, `GET .../aichat/debug-context`) forwards an arbitrary OpenAI-compatible body to the selected backend with no bound on the outbound payload. It was already a raw Gladys Plus proxy; with a personal API key or a host model behind it, it is **admin-only** like the debug context itself. Household users talk to the assistant through `message.create` and the MCP tool-calling loop only, which build the request themselves.
- **Trust, said plainly**: the AI provider sees every chat message, the conversation history, the tool schemas and tool results (device states, sensor values), and chat images (vision requests pass the OpenAI `image_url` content through; a text-only provider errors on them) — and its completions **drive the tool-calling loop with the user's authority**. That is the highest trust class an integration can hold; the store install screen of a `type: "ai"` integration says it in those terms, the selection card restates it (the GitHub and dev installs show no install screen), and the user docs (B.12) spell it out. Speech is out of scope of this type: STT/TTS keep their existing channels, only the **text** intelligence goes through the provider.

## Running a model on the host (documented setup, no core change)

A local model is the privacy case the type exists for, and the sub-container limits (B.2: 4096 MB, 2 CPU, `/dev/dri` as the only GPU class) make an inference server **inside** a sub-container a small-CPU-model affair only. The setup that works today is a **model server on the host**, reached by the integration like any LAN service:

- The gateway of the `gladys-integrations` network, **`172.30.0.1`**, is the host: integrations already reach the host API through it. Ollama listens on `127.0.0.1` by default, which a container cannot reach; `OLLAMA_HOST=172.30.0.1:11434` makes it reachable from the integrations without exposing it to the LAN (start it after `docker.service`). An integration can derive its default endpoint from the hostname of `GLADYS_HOST_API_URL`.
- **Accepted risk, to document on the integration side**: the `icc` isolation separates integrations from each other, not from the host — every installed integration can reach that Ollama, which has no authentication.
- **Context window**: the system prompt is ~2k tokens and the `scene_create` tool schema alone ~8–10k, so a scene-creation request reaches 10–15k tokens. Local runtimes often default to a few thousand tokens and **silently truncate the start of the request** (prompt and tools) without any error. The developer docs must tell AI integrations to configure it (e.g. `OLLAMA_CONTEXT_LENGTH=16384`) and to expose it in their `config_schema`.
- **No NVIDIA GPU grant to integrations**: it would need `DeviceRequests` and the NVIDIA Container Toolkit, whose root hooks on the host, driven by the image content, produced two container escapes with a malicious image (CVE-2024-0132, CVE-2025-23266). With a store without review, the sandbox would then depend on the toolkit version of each host. GPU owners run the model server natively on the host instead, as above.

## Contracts

**WebSocket (C.4 extension)** — same transport and envelope as `contracts/websocket-protocol.md`:

| Direction | `type` | Payload |
|---|---|---|
| core → integration | `external-integration.ai.chat` | `{ "message_id": "uuid", "request": { "messages": [...], "tools": [...], "tool_choice": "auto"\|"required", "max_tokens": 800, "purpose": "chat"\|"intent-classification"\|"weekly-digest", "categories": [...] } }` — an AI request routed to the integration because it is the selected AI provider. `request` is an **OpenAI-compatible chat completion request** (the `model` field is stripped by the core; `tools`, `tool_choice`, `max_tokens` and `categories` are present when the caller set them); respond via `command-result` with `data` = an **OpenAI-compatible completion** (`choices[0].message` with `content` / `tool_calls`), bounded by the core as described above; ack expected within **120 s** (**20 s** when `purpose` is `intent-classification`) |

**Management API (C.5 extension)** — dedicated literal routes, outside `/external_integration` (the choice includes Gladys Plus, which is not an external integration), standard Gladys user auth:

| Method & route | Body → Response |
|---|---|
| `GET /api/v1/ai_provider` | → `{ "selector": "ext-..." \| null, "providers": [ { "selector", "name", "status" } ] }` — `selector` null = Gladys Plus (default); `providers` = the installed `type: "ai"` integrations. Authenticated (the chat hides its model selector and the scene editor its upsell when an external provider is active; the payload carries nothing operational) |
| `POST /api/v1/ai_provider` *(admin)* | `{ "selector": "ext-..." \| null }` → `200` same shape as the `GET`; `null` (or no `selector`) resets to Gladys Plus; an installed integration that is not an `ai` one → `400`; an unknown selector → `404` |
| `DELETE /api/v1/external_integration/:selector` *(admin)* | unchanged otherwise (`contracts/management-api.md`): if the integration was the selected AI provider, `AI_PROVIDER` is cleared (back to Gladys Plus) |

**JS SDK (C.8 extension)** — `GladysAssistant/integration-sdk-js`:

| Method | Signature & behavior |
|---|---|
| `onAiChat(cb)` *(forthcoming — `GladysAssistant/integration-sdk-js`, not released yet; until it ships an integration handles the `external-integration.ai.chat` message above itself, over the C.4 WebSocket, and acks with `command-result`)* | `(request) => Promise<object>` — handler of the `ai.chat` relay (`type: "ai"` integrations only): receives the OpenAI-compatible chat completion request above (`purpose` is `chat`, `intent-classification` or `weekly-digest`), resolves an OpenAI-compatible completion (it goes into `data`; 120 s ack delay, 20 s for `intent-classification`). The SDK carries no OpenAI client: the integration brings its own |

**Store**: the canonical `manifest.schema.json` of `GladysAssistant/integration-store` must carry `"ai"` in the `type` enum for store-published AI integrations to be indexed; until it does, `type: "ai"` integrations are absent from the catalog but fully installable through "Install from GitHub" (`repo_url`) and dev mode — a core that accepts `ai` before the catalog lists it degrades gracefully in either order.

## Tests

- **Manifest** (`validateManifest`): `type: "ai"` accepted (device-agnostic fields still allowed), `messaging` / `contact_schema` still rejected outside communication; the vendored `manifest.schema.json` carries the enum value.
- **Relay** (`externalIntegration.aiChat`): request relayed with the 120 s timeout (20 s for `intent-classification`); a request settling after an uninstall leaves no counter behind; completion bounded (unknown fields and extra choices dropped, `content` capped, tool calls reduced and capped, `arguments` defaulting to `"{}"`); malformed completions (no object `choices[0].message`, non-string `content`, malformed or oversized tool calls, too many tool calls) → `EXTERNAL_INTEGRATION_INVALID_AI_RESPONSE`; disconnected integration → throw; in-flight cap per integration (the fifth concurrent request fails with `EXTERNAL_INTEGRATION_AI_PROVIDER_BUSY`, another integration is not affected, the slot is released when a request settles or fails).
- **Proxy service**: `ai.chat` exposed on an `ai` integration only.
- **Routing** (`gateway.aiChat`): variable set → proxy called with `model` stripped and hints passed through, the plan gate not consulted (a paused subscription reaches the provider); proxy missing or without `ai` capability → error, Gladys Plus never called; variable absent → Gladys Plus path untouched, model normalization included.
- **Failure replies**: a relay failure (`ExternalIntegrationUnavailableError`) in the chat loop answers `openai.provider-unavailable`, the in-flight cap `openai.provider-busy`, any other error the historical `openai.request.fail`; the brain answers exist in every brain language.
- **Gates**: `message.create` engages the AI path with an external provider and no Gladys Plus (and still replies "Plus required" with neither); `sendWeeklyDigest` sends through an external provider with Plus unconfigured and its subscription inactive, one admin at a time; `POST /api/v1/gateway/aichat/chat` answers `403` to a non-admin; the scene `ai.ask` action aborts with `AI_REQUEST_FAILED` on a `null` result and runs nothing after it.
- **Selection** (`setAiProvider` / `getAiProviders` / `GET`+`POST /api/v1/ai_provider`): list limited to `ai` integrations; selection persisted; `null` reset; `400` on a non-ai integration; `404` on an unknown selector; rollback when the provider row vanished after the write; read open to non-admins, write admin-only; uninstall of the selected provider clears `AI_PROVIDER`, uninstall of another integration keeps it.

## Verification (manual e2e, environment with the Docker socket)

Dev-install a `type: "ai"` manifest whose container answers `ai.chat` (an adapter to any OpenAI-compatible endpoint — a host Ollama through `172.30.0.1:11434` is the local case); the install screen (store path) carries the trust warning and names where the selection happens → the install lands on the configuration screen, which opens with the next-step card ("installed but unused", **Use as AI provider**), the page shows Configuration / Supervision / Logs only, the catalog card sits under *Voice assistants & AI* for an admin and is absent for a non-admin → either click **Use as AI provider** (the card turns "active", linking to the AI settings) or, on the AI settings page, pick it in the provider select; selecting it shows the trust warning and the "the assistant now uses X" line, hides the Plus upsell / quota / rate-limit note, offers the weekly digest settings and the debug download to an admin even without Gladys Plus (a non-admin sees neither, and reads in the page intro which provider the conversations go to); the chat model selector disappears, the empty chat no longer upsells Plus, the scene `ai.ask` editor names the provider → a chat message reaches the integration (its logs show an `intent-classification` request then the `chat` one, no `model`), a tool call it returns is executed by the core, the answer comes back in the chat → stop the integration: the AI settings page warns "provider not running", the next message answers `openai.provider-unavailable` (naming the integration page and the AI settings), nothing reaches Gladys Plus → start it again, send five concurrent `ai.ask` scenes: the fifth answers `openai.provider-busy` and that scene aborts with `AI_REQUEST_FAILED`, the others answer → uninstall it: the confirmation says the assistant switches back to Gladys Plus, and afterwards the select is back on Gladys Plus.

## Later leads

- **Provider per `ai.ask` action**: an optional `provider` on the action (like the `service` property of the message actions) — camera analysis on a local model, chat on a cloud one. Purely additive: the instance-wide selection stays the default.
- **Selection at install time**: with this workstream Gladys Plus stays the provider until an administrator picks another one, so an instance without Plus that installs an AI integration still has to select it before the assistant answers. Selecting the integration at install (the install screen already carries the trust warning), at least when no other provider is available, is an open product question.
- A per-type `403` on the device host API for the device-less types (`communication`, `weather`, `calendar`, `provider`, `ai`, `tts`), the hardening `capabilities/provider-type.md` lists.
