# Dashboard widgets declared by integrations (design)

Goal: that an integration — external first, through the SDK — can put its own data on the dashboard **without a dedicated box type in the core**, by describing *what* to show in a declarative JSON vocabulary that the core renders. Community request, [topic 10641](https://community.gladysassistant.com/t/permettre-aux-integrations-de-declarer-leurs-propres-widgets-de-dashboard-schema-json/10641), opened by the maintainer: solar production tracking, the state of a robot vacuum, an EV charging plan, upcoming cinema releases — the data of an integration is often exactly where it makes the most sense to look at it, and today that place does not exist.

**The pilot case, and why this spec exists**: PR #3061 ("Sorties Cinéma" widget, [topic 10757](https://community.gladysassistant.com/t/widget-sortie-cinema/10757)) was technically clean and was closed on scope: it added a core lib, a native TMDB service, a box type, a scene trigger, a scheduled job, two API routes, a new external-integration *type* with its manifest field and a pivot format to keep compatible for life — one full core surface for one domain that is not Gladys' mission. Accepting it would have set the precedent of **one integration type per domain** (recipes, transport schedules, sport results, stock prices…), which is exactly the bottleneck the external-integration system was built to remove. With this capability, the poster grid becomes a `card-list` component declared by an external TMDB integration, and the UGC/Pathé/CGR integrations the author had prepared reuse it as-is: zero cinema code in the core, and the same mechanism serves the solar panel, the vacuum and the car. A large part of what that PR wrote — payload normalization and bounding, the provider relay, the widget, the tests — transposes almost directly.

**Related requests, and what this spec does with them**: [topic 10760](https://community.gladysassistant.com/t/integrations-externes-ecrans-personnalises/10760) asks for custom *pages* in the integration section (debug views, multi-step wizards, a charging history table) — the dashboard widget is the first, bounded step of that road and the "history table" case is directly covered by `status` and `card-list`; the multi-step wizard is not, and stays out of scope (see the end of this file). [Topic 9629](https://community.gladysassistant.com/t/creer-ses-propres-widgets-gladys/9629) ("create my own widgets?") is the same need from the user side: the answer is now "an integration can".

**What this is, and what it is not, compared to the field.** No major home-automation platform lets an integration ship a dashboard widget under the platform's own design rules: Home Assistant users compose cards from entities and third-party cards are free JavaScript; Jeedom plugins ship HTML templates; Homey app widgets are sandboxed web views; openHAB custom widgets are declarative YAML with an expression language. This spec sits between openHAB and iOS — declarative like the former, content produced at runtime like the latter — and it targets the **domain widgets** Gladys lacks (a vacuum, a charging plan, upcoming releases, next departures, pollen levels, a 3D print in progress), not the **generic control widgets** (thermostat, media player, map, energy distribution), which remain core widgets and are addressed by the dashboard spec. A widget is **read and tap**: it displays data and offers buttons; it is never a form (no slider, select or text input — the standard controls of an integration's devices come from device features through the core widgets).

## Design principles (decided with the maintainer, topic 10641 and PR #3061)

1. **The integration describes *what*, Gladys decides *how*.** No HTML, no iframe, no script, no CSS, no free colors or sizes — a philosophy choice, not a shortcut. By staying declarative, the core guarantees for every widget, third-party ones included: visual consistency (the Horizon glass theme composes on every widget exactly as on core ones), dark mode, mobile/tablet responsiveness, translations, performance, and non-regression when the interface evolves. It is the iOS/Android widget model: purely declarative, and nobody finds that ecosystem poor. It is also RFC requirement (3): *consistent UI, no code injected by integrations* (`../README.md`).
2. **The content is produced at runtime, the widget is declared in the manifest.** This is the one structural decision of this spec and it deserves its rationale. Two models were on the table: a *static layout in the manifest* bound to data through path expressions (`"value": "$.production.today"`), or a *content tree produced by the integration on demand*, in the core vocabulary. The static model needs a binding language, and a binding language never stays small: paths, then conditionals (show the "docked" row only when docked), then formatting, then arithmetic — a template engine to specify, validate and maintain forever, on both the indexer and the core. The runtime model needs none of that: an integration that wants a different layout while the vacuum is cleaning simply returns a different tree, and the core stays what it should be, **a validator and a renderer**. It is precisely how iOS (a timeline of entries, each carrying its view) and Android (`RemoteViews` built at runtime) do it. What the manifest still declares is the widget's *identity* — key, label, icon, per-instance settings — which is what the store indexer can validate at publish time, what the catalog and the install screen can show, and what the dashboard editor needs to list the widget even when the integration is stopped. The content vocabulary is itself a published JSON schema, so an AI (or the SDK in dev mode) can validate a payload before sending it — the "validatable JSON" benefit of the request holds in both models.
3. **A widget cannot be ugly by construction.** Style is not the only way to ruin a card: clutter is the other one, and it is the one that free composition produces — the Home Assistant dashboard failure mode. So the vocabulary constrains two things, not one: the *style* (semantic colors, curated icons, fixed image frames, no rich text) **and the composition**, through a **content budget** per widget (section 5) — one focal component, a handful of tiles, short values, bounded lists, and a **canonical order imposed by the core**. The integration chooses the components; the core arranges them. The worst possible third-party widget looks like a slightly busy core widget, which is the goal.
4. **The payload is never trusted** (B.18 doctrine): the core normalizes and bounds every content tree before it enters the frontend — a whitelist of component types and fields, bounded strings and arrays, finite numbers, validated dates, `https` links, images served from Gladys' own origin — and renders every text as escaped plain text (C.1, "rendering of every free-form text an integration publishes").
5. **Trigger, not data** (B.17 doctrine, transposed as in B.18): data enters the core through one audited pull path; the integration can only nudge "re-pull me now". The push channel carries zero state.
6. **A capability, not a type — and a home for capability-only integrations.** `widgets` is a manifest field any integration may declare on top of its primary contract: a `device` integration (the vacuum), a `weather` provider (a richer forecast panel), a `communication` channel. The technical `type` keeps naming the **primary contract** — the interface the core itself consumes (devices and states, `message.send`, `weather.get`) — and driving routing, screens, host-API surface and non-admin visibility (`integration-catalog-categories.md` §2.2). An integration whose contract is *only* made of capabilities — the TMDB case, a fuel-price widget, tomorrow a scene-trigger provider — has no primary interface for the core to consume, so it declares the new technical type **`provider`** (`capabilities/provider-type.md`, which owns the type: screens, catalog visibility, the "at least one capability field" rule and the bar for any future type): no device surface, a configuration-only page, and a manifest that must carry at least one capability. Naming that type after one capability (`widget`) was rejected: an integration providing a widget *and* a scene trigger, with no device, has to fit one type, so the type must name the shape (capabilities, no devices), not a capability. The rule this fixes for good, and that the scene-triggers-and-actions workstream will rely on: **a new contract that the core does not consume through a dedicated interface is a capability field, never a type.**
7. **Vocabulary earns its place** (the B.18 condition-enum doctrine): a component type enters the vocabulary only when the core renders it well in both themes and both densities, and the vocabulary only ever grows **additively** — an old Gladys drops the components it does not know and renders the rest, an integration states the minimum core it needs through `gladys_version`. Nothing is ever renamed or removed.

## 1. Manifest: the `widgets` field

Optional, **max 5** entries, validated by the indexer **and** the server (`validateManifest`, mirrored in the canonical `manifest.schema.json` — a new manifest field lands in the JS validator, the vendored schema and this file in the same diff). Displayed on the install screen as a dedicated disclosure line ("this integration provides dashboard widgets: Upcoming releases, …"), like the other declared contracts.

```json
"widgets": [
  {
    "key": "upcoming_releases",
    "label": { "en": "Upcoming releases", "fr": "Prochaines sorties" },
    "description": { "en": "Movies coming to theaters in your region.", "fr": "Les films bientôt en salle dans votre région." },
    "icon": "film",
    "settings": [
      {
        "key": "period_days",
        "type": "select",
        "label": { "en": "Period", "fr": "Période" },
        "default": "30",
        "options": [
          { "value": "15", "label": { "en": "15 days", "fr": "15 jours" } },
          { "value": "30", "label": { "en": "1 month", "fr": "1 mois" } },
          { "value": "60", "label": { "en": "2 months", "fr": "2 mois" } }
        ]
      },
      { "key": "region", "type": "string", "label": { "en": "Country code", "fr": "Code pays" }, "placeholder": { "en": "FR" } }
    ],
    "action_timeout_seconds": 30
  }
]
```

| Field | Rules |
|---|---|
| `key` | required, `^[a-z0-9_]{2,32}$`, unique within the manifest — the identifier in the dashboard box, the API and the WS messages |
| `label` | required, multi-language (`en` required), each value 3–30 characters — the picker tile's name and the default card title |
| `description` | optional, multi-language, each value ≤ 100 characters — shown under the tile in the picker and on the install screen |
| `icon` | optional, `^[a-z0-9-]{1,40}$`, the name of a Feather icon (the set the picker already uses, `fe-<name>`); an unknown name renders the generic widget icon, never an error — a cosmetic field never rejects a manifest |
| `settings` | optional, ≤ 10 fields, **the `config_schema` grammar** (C.1) rendered and validated by the same engine, with three restrictions: types limited to `string` \| `number` \| `boolean` \| `select` \| `multi_select` \| `section` — `secret`, `oauth2` and `account_link` are **rejected** (settings live in the dashboard's JSON, readable by every user of a public dashboard: nothing sensitive belongs there, and linking an account is integration-scoped, not per widget); `{{port:<name>}}` placeholders are **rejected** (the editor is reachable by non-admins, whose reduced view carries no container state — the exact reason they are refused in `contact_schema`, C.1; `{{gladys_host}}` stays allowed); `source: "devices"` is **allowed** and is the intended way to bind a widget instance to one of the integration's devices ("which vacuum does this widget show") — the user picks a device by name, the integration receives its `external_id` |
| `action_timeout_seconds` | optional, integer 5–120, default 30 — the ack delay granted to `widget.action` (section 7), the same exception to the 5 s rule as manifest `actions` |

Any structural error rejects the manifest (indexer and server), like every other field. Declaring `widgets` requires `gladys_version` ≥ the first release whose validator accepts it — older cores reject unknown manifest fields (the `categories` note, C.1).

**Widget-only integrations** (the TMDB case, a fuel-price widget) declare the technical type **`provider`**, specified in `capabilities/provider-type.md`: `widgets` is the first field of its capability list, and declaring it satisfies the type's "at least one capability field" rule. Nothing else in this file depends on the type: `device`, `communication` and `weather` integrations declare `widgets` exactly the same way.

## 2. Dashboard side: the `external-widget` box

One new core box type serves every integration widget: `DASHBOARD_BOX_TYPE.EXTERNAL_WIDGET = 'external-widget'`. Box config, additive fields on the shared Joi box schema of `server/models/dashboard.js`:

```json
{ "type": "external-widget", "integration": "ext-tmdb", "widget": "upcoming_releases", "name": "Cinéma", "settings": { "period_days": "30", "region": "FR" } }
```

- `integration` (required): the `t_service` selector of the installed integration; `widget` (required): the declared `key` (same regex); `name` (optional, ≤ 40): the card title, defaulting to the widget's localized `label`; `settings` (optional): an object of `key → value` for the declared `settings`, **bounded in size** — ≤ 10 keys, string values ≤ 100 characters, **≤ 1 KB serialized** (it travels URL-encoded in the query string of the content route, section 3, so this cap is also an HTTP request-line budget: a select value, a number, a boolean or a short list of device `external_id`s fit comfortably, a free-text blob does not belong in a widget setting) — but **not validated against the manifest by the dashboard model** — the box schema is static and manifest-independent, and a manifest can change under a saved box on every integration update, so a stale setting has to degrade at render time whatever happens at save time. The validation that must exist is therefore the render-time one (section 3: `422` → the widget's "check the widget settings" state, which the editor canvas shows live as the user fills the form); the editor renders the form with the same engine (required markers, bounds, option lists), and the core applies the declared `default`s to missing keys before validating, exactly like the config form.
- **Not a device-referencing field** in the sense of `device-migration.md` B.3: a `source: "devices"` setting holds an external integration's `external_id` (always a *destination*-side device of a migration, never a source), so B.3 and `device.migrate` are unchanged.
- **Uninstall does not rewrite dashboards** (consistent with device deletion today): the box stays and renders the "integration not installed" state with a hint to remove it; reinstalling the same integration (same selector) brings the widget back untouched.

**Picker.** The searchable tile grid of the editor (`SelectBoxType`, `dashboard-flexible-layout-and-widgets.md` A.3) lists, after the core tiles, **one tile per widget of every installed integration** — localized label, declared icon, the integration's name as a caption, searchable like the others. The list comes from a new endpoint, **`GET /api/v1/external_integration/widget`**, open to every authenticated user (dashboards are per-user, and the non-admin reduced view of `GET /api/v1/external_integration` deliberately hides device integrations — C.5): it returns, for each widget of each installed integration, `{ integration_selector, integration_name, integration_status, key, label, description, icon, settings }` — the declaration, plus **one operational field, on purpose: `integration_status`**. This is a **deliberate exception to C.5**: a non-admin cannot list device integrations anywhere else (`GET /api/v1/external_integration` returns only communication integrations to them, and `GET .../:selector` 404s), yet the dashboard cannot honor RFC requirement (2) — a stopped integration visible *as stopped*, never as a spinner — without knowing the status. Nothing else operational travels (no version, no update flag, no containers, no config), the same reasoning as `GET /api/v1/weather/provider` (B.18). An implementer must not "fix" this route by filtering device integrations out for non-admins: that would resurrect the zombie widget. A literal route declared before `:selector`, like `store` and `hardware`.

**Edit form.** Title + the `settings` form rendered by the shared `config_schema` engine (`ConfigSchemaForm`, moved from the integration page into a shared component — one engine, one look, one set of tests), `source: "devices"` options loaded from the standard `GET /api/v1/service/:selector/device` (authenticated, not admin — devices are visible to every user). If the integration is not `RUNNING`, the form shows its status and stays editable (the box can be prepared while the integration restarts). A widget whose `settings` are empty shows only the title field.

## 3. The data path: pull, normalize, cache, nudge

**Route (front → core)**: `GET /api/v1/external_integration/:selector/widget/:key/content?settings=<url-encoded JSON>`, standard user auth, any authenticated user. The core:

1. resolves the integration (`404` unknown selector or key not declared in its manifest);
2. **validates the settings** against the declared `settings` schema with the shared validation engine — defaults applied to missing keys, `source: "devices"` resolved dynamically against the integration's own devices (the C.1 dynamic-value rule), unknown key or invalid value → `422` naming the key;
3. looks up the **content cache** by `(service.id, key, canonical JSON of the validated settings, language, units)` — canonical JSON = keys sorted lexicographically at every depth, arrays kept in order, no whitespace; `language` is the requesting user's ISO 639-1 language (`fr`, `en`… the value `weather.get` already sends), `units` their preference (`metric` \| `us`, as in `weather.get`), both **server-derived from the session, never taken from the query**, and both part of the key because the integration is expected to localize from them (the cinema pilot returns titles in the user's language as plain strings): a French and an English user of one public dashboard hold two cache entries, never one; a hit is returned as-is;
4. on a miss, sends **`external-integration.widget.get`** `{ message_id, key, settings, language, units }` with a **15 s** ack deadline (the same exception to the 5 s rule as `camera.get-image` and `weather.get`: a widget typically calls a third-party API). Concurrent requests for the same cache key while a command is in flight **share that command** (coalescing: ten open tablets never mean ten commands). **Pulls are bounded** like every user-triggered path: at most **2 `widget.get` commands in flight per integration** (further misses queue), and **30 cache-miss commands per minute per integration**, beyond which the route answers `429` (`TooManyRequests`) — an authenticated user cycling through valid settings cannot turn the cache into a command generator against the integration, nor evict the entries the other users rely on faster than they are refilled;
5. runs the ack's `data.content` through **`normalizeWidgetContent`** (sections 4 and 5), **resolves the device references** within the tenant (section 8), stores the result with its TTL, returns it.

**Response (`200`)** — the normalized content, never the raw payload:

```json
{
  "expires_at": "2026-09-18T09:12:30.000Z",
  "content": {
    "version": 1,
    "components": [
      { "type": "value", "label": { "en": "Battery", "fr": "Batterie" }, "device_feature": "ext:ext-roborock:s7:battery", "device_feature_selector": "roborock-s7-battery" },
      { "type": "status", "items": [ { "label": { "en": "State", "fr": "État" }, "value": { "en": "Docked", "fr": "Sur la base" }, "color": "success" } ] },
      { "type": "image", "key": "cleaning-map-3f9a2c", "alt": { "en": "Last cleaning map", "fr": "Carte du dernier nettoyage" } },
      { "type": "button", "label": { "en": "Start", "fr": "Démarrer" }, "style": "primary", "action": { "key": "start", "params": { "mode": "full" } } },
      { "type": "button", "label": { "en": "Dock", "fr": "Base" }, "device_feature": "ext:ext-roborock:s7:dock", "value": 1, "device_feature_selector": "roborock-s7-dock" }
    ]
  }
}
```

- `expires_at` replaces the content's relative `ttl_seconds` with the absolute instant (ISO 8601, UTC) after which the frontend refetches; the cached entry and every response served from it carry the same value.
- `content` is exactly what the frontend renders: the components that survived normalization and the budget, **in the order the integration sent them** (the canonical order of section 5 is applied at render time, so the same response feeds the editor preview and the dashboard); every field is already bounded, every text still in its multi-language or string form (the frontend picks the language), every date still ISO (the frontend formats).
- Every accepted device reference is **kept as sent and completed with its resolution**: `device_feature` → `device_feature_selector` (string) on `value`, `gauge` and `button`; `device_features` → `device_feature_selectors` (array, same order) on `chart`. The frontend only ever uses the selectors (batch load, WebSocket updates, history, commands) and never sees a reference the tenant check refused — that component is simply absent.
- Image keys and action keys come back as sent: the frontend requests images through the image route (section 6) and posts actions through the action route (section 7) with those keys, and the core checks both against this very content.

**Errors**, translated so no internal code ever reaches the user as an opaque "unknown error": integration not connected, ack timeout, `success: false`, invalid payload → `400 REQUEST_TO_THIRD_PARTY_FAILED` (the standard code the weather widget already maps to its call to action), with the integration's own `error` string, when present, bounded to 200 characters and returned alongside — displayed as escaped plain text under the generic message ("API key invalid" is more actionable than "unavailable"). One invalid payload is told apart: a content `version` higher than the core supports → `400` with the dedicated code **`WIDGET_CONTENT_VERSION_UNSUPPORTED`** (a new `ERROR_MESSAGES` entry), which the frontend maps to its "needs a newer Gladys" state — the one failure whose remedy is on the user's side, not the integration's, so it must not read as "unavailable". The frontend never fetches while it knows the integration is `STOPPED`, `ERROR` or `DISABLED` (section 12): those are statuses, not failed requests. `DEGRADED` is **not** one of them — a degraded integration is a live container that missed pongs (B.1) and still answers commands, so the widget keeps pulling and lets a dead command surface as `REQUEST_TO_THIRD_PARTY_FAILED`.

**Cache.** The content carries its own freshness, `ttl_seconds` (integer, clamped to **10–3600**, default 60 when absent) — the reload policy of an iOS timeline entry, chosen by the one who knows how fast the data moves (cinema releases: an hour; a vacuum: 30 s). The cache is in memory (`this.cache`, the same store as the weather images), **≤ 50 entries per integration** in LRU order (language and unit variants count as entries), and is dropped in full for an integration when it stops, restarts, updates or is uninstalled. The response carries `expires_at`; the frontend refreshes on expiry, so a widget with `ttl_seconds: 300` self-refreshes every 5 min with one command whatever the number of open dashboards.

**The freshness nudge** — `external-integration.widget.refresh` `{ key }` (integration → core, no `message_id`, no ack, fire-and-forget) means only "re-pull me now": the core drops the cached contents of `(service, key)` and broadcasts **`external-integration.widget-updated`** `{ selector, key }` on the user WebSocket; every open instance of that widget refetches (coalesced). Rate-limited to **1 per 10 s per `(integration, key)`**, silently dropped beyond (fire-and-forget has no error path, and a dropped nudge costs at most one TTL). The vacuum integration nudges on every state change: the first nudge of a 10 s window wins, later ones are dropped, so the tile follows within a few seconds at worst — and the data still came in through the audited pull path.

**A nudge landing during an in-flight pull** must not let the pre-nudge tree outlive the nudge (the interleaving B.18 solves by serializing weather checks, transposed to a cache): each `(service, key)` carries a **generation counter**, incremented by every invalidation (nudge, successful action, lifecycle change). A `widget.get` command is stamped with the generation current at its start; a result that arrives under a **newer generation is served to the callers already waiting on it but never written to the cache**, and a request arriving after the invalidation never coalesces onto a stale in-flight command — it starts (or joins) a new command for the new generation. A lifecycle change (stop, update, uninstall) **moves** the generation of every widget the same way, never resets it, and drops the in-flight commands: a pull started before the stop cannot refill the cache when it lands, and a dashboard refetching after the restart never coalesces onto it. **Images follow the same rule** under one integration-scoped generation (a pseudo widget key the manifest cannot declare): a `widget.get-image` started before the stop is served to its callers but never cached, so a cleaning map or poster cannot outlive a restart for the image TTL. The wall tile therefore always ends up on the post-nudge state, at the cost of at most one extra command per nudge.

Documented limitation (accepted): 10 s is the floor of nudge-driven freshness — a cleaning map redrawn every second is not what a dashboard card is for; the live values that need to move every second are device features, which section 8 binds to the core's own real-time path.

## 4. The content vocabulary

What `widget.get` resolves with — `data.content`:

```json
{
  "version": 1,
  "ttl_seconds": 1800,
  "components": [
    { "type": "text", "variant": "caption", "text": { "en": "Next 30 days · France", "fr": "30 prochains jours · France" } },
    {
      "type": "card-list",
      "display": "grid",
      "items": [
        {
          "title": "L'Odyssée",
          "date": "2026-10-07",
          "image": "poster-20637522",
          "badge": { "text": { "en": "New", "fr": "Nouveau" }, "color": "info" },
          "description": "Après la mort de son père, …",
          "links": [
            { "url": "https://www.youtube.com/watch?v=…", "label": { "en": "Trailer", "fr": "Bande-annonce" } },
            { "url": "https://www.themoviedb.org/movie/20637522", "label": "TMDB" }
          ]
        }
      ]
    }
  ]
}
```

**Envelope**: `version` (integer **≥ 1**, optional, default `1`; `0`, a negative or a non-integer value is an **invalid payload** — refused like a timeout, `400 REQUEST_TO_THIRD_PARTY_FAILED`; a version **higher than the core supports** is refused as a whole with the dedicated `WIDGET_CONTENT_VERSION_UNSUPPORTED` code (section 3) — the widget renders "this widget needs a newer Gladys", honest and debuggable — while version 1 stays forward-compatible by the drop rules below, so a bump will only ever happen for a breaking change, which this doctrine is designed to avoid), `ttl_seconds` (section 3), `components` (array, bounded by the content budget of section 5; an empty array renders the translated empty state — a widget with nothing to show is a valid state, not an error). A raw `content` above **256 KB** is treated as an invalid payload.

**Normalization rules** (`normalizeWidgetContent`, the `normalizeWeather` pattern): whitelist per component type — **unknown fields are dropped**; a component of **unknown `type` is dropped** with a warning log (forward compatibility: a newer integration on an older core renders partially rather than not at all); a component **missing a required field is dropped**, never the whole content (optional metadata never rejects, and one bad item never blanks a widget); the same applies item by item inside `items`, `series` and `links`. Numbers must be finite; strings are trimmed, stripped of control characters and **truncated to their bound with an ellipsis**; every text field accepts a plain string **or** a multi-language object (`en` required for the fallback, C.1 language rule); `date` fields are ISO 8601 strings parsed by the core, formatted in the **user's locale and timezone** at render time, dropped when invalid (the integration sends raw values, the core formats — same for numbers, whose digits and separators follow the account language); `url` fields are `https` only, ≤ 2048 characters, **without credentials** (`user:pass@` is dropped) and served in their **normalized form** (the `href` the parser validated, never the raw string), opened in a new tab with `noopener noreferrer` and the **target domain displayed** next to the label (the C.1 section-links rule: unmoderated third-party content, the user sees where they click); `icon` is a Feather icon name (`^[a-z0-9-]{1,40}$`, unknown → no icon); `color` is a **semantic enum** — `neutral` \| `primary` \| `success` \| `warning` \| `danger` \| `info` — mapped by the core to theme colors in both modes, never a hex value.

**Components** — every text bound is in characters, per language value; the counts per widget are those of the content budget (section 5). Three **live-binding** forms (`device_feature`, `device_features`) are specified in section 8 and listed here for completeness:

| `type` | Fields | Renders as |
|---|---|---|
| `text` | `text` (required), `variant` (`heading` \| `body` \| `caption`, default `body`) | escaped plain text. `heading` (≤ 40) and `caption` (≤ 80) are **single-line** (line breaks removed, ellipsis on overflow): a section title, a muted subtitle. `body` (≤ 300) honors line breaks (`white-space: pre-wrap`, C.1) with at most one blank line in a row (longer runs of line breaks are collapsed) — a sentence or two, never a layout drawn in text; long texts belong in a `card-list` detail panel |
| `value` | `value` (required: number, or string ≤ 12), `label` (≤ 24), `unit` (≤ 6), `icon`, `color` — **or** `device_feature` in place of `value`/`unit` (section 8) | a **tile** — the visual family of the temperature tile and the chips: one short value, one unit, one label. A sentence cannot fit in a tile by construction |
| `gauge` | `value` (required, number), `min`, `max` (required, finite, `min < max`), `label` (≤ 24), `unit` (≤ 6), `color` — **or** `device_feature` in place of `value`/`unit` (`min`/`max` default to the feature's) | a tile-sized radial arc — the visual family of the gauge box, drawn in SVG so a tile stays light (no per-widget thresholds: `color` is the whole styling) |
| `status` | `items` (required, 1–10 of `{ label (required, ≤ 40), value (required: number or string ≤ 40), icon, color }`) | a list of label / value rows with a colored dot — the "list of states" of the request (vacuum: state, battery, area cleaned; charging: plan, kWh, cost). Ten rows is the height of a card; a longer table is not a dashboard widget |
| `chart` | `series` (required, 1–4 of `{ name (≤ 24), points (required, 1–300 of { t: ISO date, v: number }) }`) **or** `device_features` (1–4) + `interval` (the chart box's interval enum: `last-hour` \| `last-twelve-hours` \| `last-day` \| `last-three-days` \| `last-week` \| `last-month` \| `last-three-months` \| `last-year`; absent or unknown → `last-day`; section 8), `chart_type` (`line` \| `area` \| `bar` \| `stepline`, default `line`), `title` (≤ 40), `unit` (≤ 6), **`annotations`** (optional, ≤ 8 of `{ t (required, ISO date), value (number), label (≤ 16), color }`, on either form), **`now_marker`** (boolean, default `false`) | the ApexCharts rendering shared with the chart box, series colors from the chart box's default palette in order, fixed height — **zero styling** from the integration. Inline series carry data the core has no history of (a production forecast, a charging plan, hourly prices). **Annotations are the points a curve is read for** (field feedback, topic 10641, the tide widget: "07h48, 10,69 m, coef. 74" is the information, the curve is its context — the same for a solar peak, a tariff slot, a predicted end of charge): the core draws an annotation with a `value` as a **dot on the curve** at `(t, value)`, one without as a **vertical line** at `t`, each with its short label in its semantic color; `now_marker` draws a **dashed line at the current time**, labelled by the core in the user's language, only when the plotted series span that instant (a forecast for tomorrow has no "now"). An annotation whose `t` is invalid is dropped, the 9th is dropped; the core never invents an axis range for them — a marker outside the data is simply off the chart |
| `card-list` | `display` (`grid` \| `list`, default `list`), `items` (required, 1–12 in `grid`, 1–8 in `list`, of `{ title (required, ≤ 60), subtitle (≤ 60), date (ISO), image (image key, section 6), badge ({ text ≤ 16, color }), description (≤ 2000), links (≤ 3 of { url, label ≤ 24 }) }`) | `grid`: a responsive poster grid (2:3 image frame, title clamped to two lines, date) — the cinema case; `list`: rows (square thumbnail, title, subtitle or date, badge). Tapping an item with a `description` or `links` opens the core's **detail panel** (title, date, description as pre-wrap plain text, links with their domain): "synopsis, trailer, TMDB link" with no widget-specific code. Beyond the cap, the integration sorts by relevance and sends the first items: a dashboard shows what matters now, not an archive |
| `image` | `key` (required, image key, section 6), `alt` (≤ 100), `fit` (`cover` \| `contain`, default `cover`) | an image in a **fixed 16:9 frame** at the card width (the height is the frame's, never the image's), served through the core — a vigilance map, a solar layout, a robot's cleaning map, a webcam snapshot |
| `button` | `label` (required, ≤ 24), `icon`, `style` (`primary` \| `secondary` \| `danger`, default `secondary`), and exactly one of `action` (object), `device_feature` (`external_id`, with a sibling `value`) or `link` (object) — section 7 | a pill button in the quick-actions visual family |

**One shape for every device reference**: wherever a component points at one of the integration's features — `value.device_feature`, `gauge.device_feature`, `button.device_feature`, each entry of `chart.device_features` — the field is the feature's **`external_id` as a plain string**, exactly as the integration published it (`gladys.externalId(...)` in the SDK), and the core answers with the sibling `device_feature_selector` / `device_feature_selectors` (section 3, response). A `button` adds the `value` to send next to it, the shape of the quick-actions box config (`{ device_feature, value }`). No `{ external_id }` object anywhere: one field name, one type, one resolution rule.

**Versioning of the vocabulary** ("versionner le schéma", topic 10641): the vocabulary is published as **`widget-content.schema.json`** next to `manifest.schema.json` (canonical owner `GladysAssistant/integration-store`, vendored copy in the monorepo, the core's `normalizeWidgetContent` being the enforcement that mirrors it — the manifest pattern). Evolutions are **additive only**: a new component type, a new optional field, a new enum value — each shipped when the core renders it, never before, and each harmless to an older core (dropped) and to an older integration (absent). The envelope `version` exists for the breaking change the doctrine intends never to make.

## 5. The content budget: what a widget may contain, and in which order

A card has a size; so does what fits in it well. The budget below is enforced by `normalizeWidgetContent` **after** the per-component rules of section 4: components beyond a cap are **dropped in content order** with a warning log (the first ones win — the integration puts what matters first), never rejected as a whole. The SDK's dev-mode validator (section 11) reports the same violations to the developer, so a widget that ships is a widget that fits.

| Rule | Bound | Why |
|---|---|---|
| **Components per widget** | **8** | a card is read at a glance; beyond, it is a page |
| **Focal component** — `chart`, `card-list`, `image` | **at most one** | one card, one subject: a chart *and* a poster grid are two widgets (an integration may declare five). Two `status` lists count as one focal component too: the second is dropped |
| **Tiles** — `value`, `gauge` | **≤ 6**, rendered as one wrapping row | a stats banner (three values), a battery next to a state; six tiles already fill two rows on a phone |
| `text` | **≤ 2**, of which at most one `body` | a heading or caption sets the context, a body explains an empty or degraded state; a widget is not prose |
| `status` | **≤ 1** (10 rows, section 4) | one list of states per card |
| `button` | **≤ 4**, rendered as one wrapping row | one tap = one action; four is a full row on a phone |
| Lists and grids | `status` 10 rows, `card-list` 12 in `grid` / 8 in `list`, no internal scrolling | the card's natural height stays that of a core widget; content is trimmed, never scrolled |
| Text | single-line `heading`/`caption`, `body` ≤ 300 with collapsed blank lines, tile value ≤ 12, tile label ≤ 24 | no paragraph in a tile, no layout drawn with line breaks |
| Images | `image` in a 16:9 frame, `grid` thumbnails 2:3, `list` thumbnails square, `fit` cover/contain | an image can never distort a card |

**Canonical order — imposed by the core, not chosen by the integration.** Whatever the order of `components`, the card renders its content in five fixed slots, each optional: (1) **header text** — a `heading` and/or a `caption`; (2) **tiles** — the `value`/`gauge` row; (3) **focal component** — the `chart`, `card-list` or `image`; (4) **status** — the `status` list, preceded by the `body` text if any; (5) **buttons** — the `button` row. Within a slot, content order is preserved (the integration decides which tile comes first). This is the strongest guarantee of this spec: two integrations that show "a value, a curve and two buttons" produce two cards with the same silhouette, and no integration can produce a disordered one. It costs the integration nothing it legitimately needs — a card that wanted its buttons above its chart wanted to be a page.

Together with the style rules of section 4 (semantic colors, curated icons, no rich text, fixed frames), the budget is what makes principle 3 hold: every widget an integration can express is a widget the core would have designed.

## 6. Images

Images never come from a third-party URL loaded by the browser: the user's IP would reach the third party on every dashboard render (the catalog cover doctrine, C.1, and the exact objection raised on PR #3061 — posters loaded from `image.tmdb.org`). And the core does not fetch third-party URLs on the integration's behalf either: the core sits on the host network while the integration is sandboxed, so an integration-supplied URL fetched by the core is a request into the LAN from a container that should not have that reach — a server-side request forgery by construction. So the **integration serves the bytes on demand**, the B.18 point 6 mechanism generalized:

- the content only ever declares **keys** (`image` fields: `^[a-z0-9][a-z0-9-]{0,63}$`); the bytes travel over **`external-integration.widget.get-image`** `{ message_id, image_key }` → `command-result` `data.image` (raw base64, no data-URI prefix; **15 s** ack), and the core validates the **decoded bytes**: PNG, JPEG or WebP by magic numbers (WebP joins the weather set because it is the format every poster CDN serves, and the dashboard assets already accept it), **≤ 300 KB**, and a **pixel size read from the header** (PNG `IHDR`, JPEG `SOF` frame header, WebP `VP8`/`VP8L`/`VP8X` chunk) of **at most 4096 × 4096** — a 300 KB file can decode to a gigantic bitmap in the browser, so the bound is enforced before the bytes are cached or served, and an unreadable header fails closed. **Each refusal names its rule**: `EXTERNAL_INTEGRATION_WIDGET_IMAGE_TOO_LARGE`, `EXTERNAL_INTEGRATION_WIDGET_IMAGE_UNSUPPORTED_FORMAT`, `EXTERNAL_INTEGRATION_WIDGET_IMAGE_DIMENSIONS_EXCEEDED` (an unreadable header included), `EXTERNAL_INTEGRATION_INVALID_WIDGET_IMAGE` for a missing or empty payload — each with a core-authored detail stating the measured value against the bound (`378 KB received, 300 KB allowed`, `5000×3000 px, at most 4096×4096 allowed`), **logged at warn level with the integration selector and the image key**, and echoed as the `error` of the image route's `400 REQUEST_TO_THIRD_PARTY_FAILED`. The frontend shows the same broken frame whatever the reason; the developer reads *why* in the Gladys logs or in the response, never has to trace it (field feedback, topic 10641: a single opaque code cost the cinema integration's author an afternoon on posters the CDN served at 340–380 KB);
- **the integration resizes, the core never recompresses.** Poster CDNs and webcams routinely serve files above the cap, and the integration cannot always ask the source for a smaller one — so it produces one itself: it runs in its own container, `sharp` (or any resizer) at the *display* width is a three-line step in its `onWidgetGetImage` handler, and the display width is small by construction (a `card-list` grid poster is rendered under 300 px wide, a 16:9 `image` frame under 800 px; a 380 KB poster resized to 300 px and encoded as WebP weighs a few tens of KB). The core **validates and refuses, it never repairs**: recompressing on the core would put third-party-triggered CPU and memory on the host, in a path every dashboard render can hit, and a bound the core silently works around is no longer a bound — integrations would send whatever they fetch. The SDK documentation and the template show the resize step, and the SDK dev mode (section 11) checks the image before it leaves the integration;
- **image keys are integration-scoped**, not widget-scoped: two widgets of one integration showing the same poster share one key, one download, one cache entry. The allowlist is the union of the keys declared in the integration's currently cached contents: a key declared nowhere `404`s **without a single byte sent to the integration**; the route shape-checks the key against the regex before consulting anything;
- **a key is immutable for the life of the cache**: the core caches by key alone, so an integration whose image changes while its key stays (a robot's `cleaning-map` redrawn every minute) would be shown an hour-old map with no way to bust it. The rule is the one every CDN applies: **when the bytes change, the key changes** — a content-addressed suffix (`cleaning-map-3f9a2c`) or a timestamp — and the old key leaves the content, hence the allowlist, on the next pull. The template and the SDK documentation state it; a poster's key (`poster-20637522`) is naturally stable, a live map's key is naturally not;
- served to the frontend from Gladys' own origin — **`GET /api/v1/external_integration/:selector/image/:image_key`** (standard user auth, the `content-type;base64,data` shape of the weather image route), cached **1 h** per `(integration, image_key)`, ≤ 100 entries per integration in LRU order (a dozen posters and a few maps fit; beyond, the oldest are re-pulled). The route sits **directly under `:selector`, not under `widget/`**, because images are integration-scoped and because a nested `widget/image/:image_key` would share its shape with `widget/:key/content` (`image` is a valid widget key, `content` a valid image key — Express would route `.../widget/image/content` to whichever was declared first). With the image route at its own path position, no widget key needs to be reserved: `.../widget/image/content` is the content of a widget keyed `image`, `.../image/content` an image keyed `content`;
- **at most 4 image commands in flight per integration**, the others queued core-side, and concurrent requests for one key share one command — a grid of 12 posters opened on three tablets costs 12 commands once an hour, never 36 at once; the integration keeps its own download cache and answers from it. The frontend **lazy-loads** images as their frame enters the viewport (the browser's native `loading="lazy"` on the frame's `img`), so a poster grid below the fold costs nothing until it is scrolled to, and the first paint of a card never waits on its images.

## 7. Actions: the `button` component

The command side of the request ("boutons"): start the vacuum, launch a charge, open the trailer. Three kinds, exactly one per button; buttons render as the last slot of the card, one wrapping row of pills (section 5).

| Kind | Fields | Tap does |
|---|---|---|
| widget action | `action` `{ key (required, ^[a-z0-9_]{2,32}$, unique within the content), params (optional object, ≤ 1 KB), confirm (boolean, default false) }` | `POST /api/v1/external_integration/:selector/widget/:key/action/:action_key` `{ settings }` → the core resolves the content **through the content path of section 3** — the same settings validation and defaults, the requesting user's session `(language, units)` variant, the same coalescing and the same 2-in-flight / 30-miss-per-minute bounds — so the allowlist is the content the acting user's dashboard shows (re-pulled when nothing is cached, never another locale's tree), then relays **`external-integration.widget.action`** `{ message_id, key, action_key, params, settings }` with the declared `action_timeout_seconds`, and shows the optional `data.message` (string or multi-language, ≤ 200 characters) as a toast. The `params` sent are **the ones declared in the last normalized content**, never taken from the request: an action key absent from that content `404`s without reaching the integration (the image-allowlist rule). `confirm: true` makes the frontend ask before sending (`danger` style suggested). **Response**: `200 { "message": <string \| multi-language object \| null> }` (the ack's `data.message`, bounded to 200 characters, `null` when the integration returned none); `404` undeclared action, `429` rate limit, `400 REQUEST_TO_THIRD_PARTY_FAILED` on timeout, `success: false` (with the bounded `error` alongside, as for content) or disconnected integration. After a successful action the core drops the cached contents of `(service, key)` and broadcasts `widget-updated`: the tile reflects the new state without the integration having to nudge. Rate limit **30 actions per minute per integration** → `429` |
| device feature | `device_feature` (required, the feature's `external_id`) + `value` (required, number) | the core resolves the feature **within the tenant** (a feature of a device of this integration's `t_service`, not `read_only`, value within `min`/`max`; anything else drops the button) and returns `device_feature_selector`; the frontend sends the standard `POST /api/v1/device_feature/:selector/value { value }` — the quick-actions path, which comes back to the integration as `device.set-value`. Active state (tint when `last_value` equals `value`) and live updates for free |
| link | `link` `{ url (required, https), label }` | opens in a new tab, domain displayed (section 4 `url` rule) |

A dashboard is editable by any authenticated user and can hang on a public wall panel: a widget action carries exactly what the *integration author* declared, no user input — the same trust level as the `actions` manifest buttons, extended to the dashboard because the vacuum's "start" belongs on the wall, not on the admin's configuration screen. The acting user's identity is **not** sent (lead: a `user` block, additive).

## 8. Live device bindings

"Comment le widget récupère ses données : features d'appareils existantes ?" — yes, for the integration's own devices, and with zero data transfer: `value` and `gauge` accept **`device_feature`** (`external_id`) instead of an inline `value`, `chart` accepts **`device_features`** (1–4 `external_id`s) plus `interval` (the chart box's interval enum) instead of inline `series`. The core resolves each reference **within the tenant** (a feature of one of this integration's devices, else the component is dropped with a warning — a widget never displays another integration's or the core's data, the user has core widgets for that) and returns the feature selector; the frontend then reuses the exact paths of the chips bar and the chart box: one `GET /api/v1/device?device_feature_selectors=` batch, live `DEVICE.NEW_STATE` updates over the user WebSocket (this is the sub-second path — a live battery or power tile moves the instant the integration publishes a state, without any nudge), `GET /api/v1/device_feature/aggregated_states` for the history with the chart box's own `max_states`/`group_by` defaults for the declared `interval` (no per-widget aggregation knobs), the feature's real unit converted to the user's preferences, the compact value rendering of `DeviceFeatureValueText` (open/closed, on/off, rounded value + short unit), the category icon by default. The solar widget shows today's production as a live tile and its 24 h curve from the history the core already keeps, and the integration's `widget.get` answer for that part is a handful of references.

## 9. Management API (front → core)

All standard user auth, every authenticated user (the dashboard's audience), `404` for an unknown integration, widget or undeclared key:

| Route | Section |
|---|---|
| `GET /api/v1/external_integration/widget` | 2 — declared widgets of every installed integration (literal route before `:selector`) |
| `GET /api/v1/external_integration/:selector/widget/:key/content?settings=` | 3 |
| `GET /api/v1/external_integration/:selector/image/:image_key` | 6 — directly under `:selector`, never under `widget/` (route-shape collision, section 6) |
| `POST /api/v1/external_integration/:selector/widget/:key/action/:action_key` | 7 |

No new host API endpoint: the nudge travels over the integration WebSocket like `weather.refresh`.

## 10. Integration WebSocket messages

Following the C.4 convention (`external-integration.<domain>.<action>`, one type per action, `message_id` + `command-result` ack unless documented):

| Direction | `type` | `payload` |
|---|---|---|
| core → integration | `external-integration.widget.get` | `{ message_id, key, settings, language, units }` — `settings` the validated `key → value` object with defaults applied, `language` ISO 639-1, `units` `"metric"` \| `"us"` → `command-result` `data.content` (section 4); ack within **15 s** |
| core → integration | `external-integration.widget.get-image` | `{ message_id, image_key }` → `command-result` `data.image` (raw base64; PNG/JPEG/WebP ≤ 300 KB decoded, ≤ 4096 px per side read from the header); ack within **15 s** |
| core → integration | `external-integration.widget.action` | `{ message_id, key, action_key, params, settings }` → `command-result` with optional `data.message`; ack within the widget's `action_timeout_seconds` |
| integration → core | `external-integration.widget.refresh` | `{ key }` — freshness nudge, no `message_id`, no ack; accepted only for a `key` declared in the manifest; rate-limited 1 per 10 s per `(integration, key)`, silently dropped beyond |
| core → frontend (user WS) | `external-integration.widget-updated` | `{ selector, key }` — open instances refetch |

Constants: `WEBSOCKET_MESSAGE_TYPES.EXTERNAL_INTEGRATION.WIDGET_GET` / `WIDGET_GET_IMAGE` / `WIDGET_ACTION` / `WIDGET_REFRESH` / `WIDGET_UPDATED`; `WIDGET_GET_TIMEOUT_MS = 15 s` in `server/lib/external-integration/constants.js`. An integration on an older SDK ignores the new types silently (C.4 forward compatibility).

## 11. SDK (`@gladysassistant/integration-sdk`, C.8)

| Surface | Contract |
|---|---|
| `onWidgetGet(key, cb)` | `({ settings, language, units }) => Promise<content>` — registered **by widget key** like `onAction`; the resolved content goes into `data.content` (15 s) |
| `onWidgetGetImage(cb)` | `(imageKey) => Promise<string>` — resolve the raw base64 of a declared image key (PNG/JPEG/WebP, ≤ 300 KB decoded); integration-scoped, one handler; a key is immutable for an hour core-side, so a changing image needs a changing key (section 6) |
| `onWidgetAction(key, cb)` | `(actionKey, params, { settings }) => Promise<string \| { message } \| undefined>` — the resolved message goes into `data.message` |
| `requestWidgetRefresh(key)` | fire-and-forget nudge (section 3); rate-limited core-side |

Dev mode: with `DEBUG=gladys-integration-sdk`, the SDK validates every content it returns against the vendored `widget-content.schema.json` **and the content budget** (section 5), and every image `onWidgetGetImage` returns against the section 6 bounds (format by magic numbers, decoded size, pixel size from the header — the developer reads "`poster-123`: 378 KB, 300 KB allowed, resize it" in the integration's own logs, before the core refuses it), and logs the violations — the integration developer sees "`items[3].title` is required" or "9 components, 8 allowed: `status` dropped" in their logs instead of a silently trimmed card. The official template (B.11) ships a **demo widget** (a `status` list, a live `value` tile bound to the demo virtual switch and a `button` toggling it) so the e2e journey of the framework (`../verification.md`) covers the whole surface.

## 12. Frontend rendering

- **One component**, `front/src/components/boxs/external-widget/`, renders every integration widget: a standard card (title = box `name` or the widget label), natural height, no stretch flag, the Horizon glass variant composed on `.glass-theme` like every widget. Inside, the five slots of the canonical order (section 5) and nothing else: no layout logic reads the content.
- **States**, each translated by the core in every language, driven first by the integration status (from the widget list, live via `STATUS_CHANGED`) and only then by the content request:

  | Integration status | The card |
  |---|---|
  | `STOPPED`, `ERROR`, `DISABLED` | **stopped**: no fetch; the status badge, and for an admin a link to the integration page — RFC requirement (2), no zombie state: a stopped integration is visible on the dashboard as stopped, never as a spinner |
  | `LOADING`, `UNKNOWN` | *loading* skeleton, no fetch yet; the first `STATUS_CHANGED` to a serving status triggers the pull |
  | `RUNNING`, `DEGRADED` | serving: the content is pulled; `DEGRADED` shows its badge next to the title but still renders content (a live container that missed pongs, B.1, still answers commands) |
  | absent from the widget list | **not installed**: "this integration is no longer installed", hint to remove the box |

  Then, from the content request: **unavailable** (`400 REQUEST_TO_THIRD_PARTY_FAILED` → "data unavailable", retry button, the integration's bounded message underneath); **check settings** (`422` → "edit this widget", the failing key named); **needs a newer Gladys** (`400 WIDGET_CONTENT_VERSION_UNSUPPORTED`); **empty** (zero components); `429` → the card keeps its last content and retries after the TTL.
- **Refresh**: on mount, on `expires_at`, on `widget-updated` for its `(selector, key)`, on `websocket.connected`, and on `STATUS_CHANGED` to `RUNNING` or `DEGRADED`; every fetch coalesced core-side. Device-bound tiles and charts additionally follow `DEVICE.NEW_STATE` like the chips bar. Images load lazily as their frame enters the viewport (section 6).
- **Chart markers**: `annotations` and `now_marker` (section 4) are turned into the ApexCharts `annotations` (points and x-axis lines) by the widget, not by the shared chart component, which only accepts them as an opaque option — the chart box renders none; colors are the vocabulary's semantic accents, the "now" label is the core's own string (`dashboard.boxes.external-widget.now`).
- **Text**: every integration string through the language fallback (`getLocalizedText`) and rendered as escaped plain text (`white-space: pre-wrap` for `body` and detail descriptions, single line with ellipsis elsewhere — C.1) — no Markdown, no HTML, anywhere in a widget; a long token wraps, a long description scrolls inside the detail panel. Dates and numbers formatted by the core in the user's locale.
- **Editor**: the edit form of section 2; the picker tile carries `data-cy="box-type-external-widget-<selector>-<key>"` for Cypress.
- i18n in **all** languages (`front/src/config/i18n/*.json`, `compare-translations`): `dashboard.boxTitle.external-widget` and the state strings; everything else comes from the manifest and the content.

## 13. Security and accepted risks

- **No code path from the integration to the browser**: the vocabulary is a closed whitelist, every text is escaped, links are `https` with their domain shown, images are validated bytes served from Gladys' origin, colors and icons are enums. The XSS surface of a third-party widget is that of a device name.
- **Tenant isolation holds**: device references resolve only inside the integration's `t_service`; an integration cannot display, chart or actuate anything it does not own.
- **Everything user-triggered is bounded**: content pulls coalesced, cached, capped in flight and rate-limited on misses, images capped in size, count and concurrency, actions rate-limited and allowlisted from the integration's own content, nudges rate-limited, settings capped at 1 KB. A misbehaving widget costs its integration's own commands, never the core's stability — a slow or crashed integration yields "unavailable" tiles, RFC requirement (1).
- **Accepted**: a widget is content chosen by an unaudited third-party author and shown to every user who adds it (the trust level of the manifest description and of the connection-status message, already accepted); a `params` object is opaque to the core and echoed as declared (bounded, never user-supplied); the acting user is anonymous to the integration (lead, section 7); the in-memory caches are lost on restart (a cold dashboard costs one pull per widget, like today's weather widget); an integration may misuse semantic colors (every row `danger`) — a taste failure the budget cannot forbid without forbidding the feature, mitigated by the fact that colors only ever tint a dot, a badge or a tile accent, never a surface.

## 14. Tests (100% patch coverage, B.13)

- **Manifest** (`validateManifest`): `type: "provider"` accepted with `widgets`, rejected without any capability field (explicit error), `widgets` accepted on `device`, `communication` and `weather` manifests too; `widgets` bounds (0 and 6 entries, key regex, duplicate keys, label/description lengths, icon regex), `settings` restrictions (`secret`/`oauth2`/`account_link` → rejected, `{{port:}}` → rejected, `{{gladys_host}}` accepted, `source: "devices"` accepted, ≤ 10 fields), `action_timeout_seconds` bounds; the vendored `manifest.schema.json` updated in the same diff.
- **`normalizeWidgetContent`**, one file per component: required fields (component dropped, siblings kept), every string bound (truncation with ellipsis, control characters stripped, line breaks removed from `heading`/`caption`, blank-line runs collapsed in `body`), multi-language fallback, unknown component type dropped with a warning, unknown field dropped, invalid/non-finite numbers, invalid dates dropped, `http` link dropped, `color`/`icon`/`variant`/`chart_type`/`interval`/`display`/`style` enums (unknown `interval` → `last-day`), per-array caps (`status` 10, `card-list` 12/8, `series` 4 × 300, `links` 3, `annotations` 8), chart `annotations` on both forms (`t` required and re-serialized as ISO, `value` finite or absent, `label` bounded to 16, `color` from the enum or absent, a non-array `annotations` ignored, no field when none survived) and `now_marker` kept only when strictly `true`, `ttl_seconds` clamping and default, `version` > 1 refused with the dedicated code, `version` 0 / negative / non-integer refused as an invalid payload, 256 KB envelope, empty `components` accepted.
- **Content budget**: 9 components → the 9th dropped; two focal components → the second dropped (each pair: chart+chart, chart+card-list, image+card-list, status+status); 7 tiles → the 7th dropped; 3 `text` or two `body` → dropped; 5 buttons → the 5th dropped; **canonical order** (buttons declared first render last; a heading declared last renders first; order preserved within a slot); a `button` with two kinds (`action` + `link`) dropped.
- **Cache and nudge**: hit/miss/TTL expiry, LRU at 50, **two users with different languages or unit systems get two entries and two commands, never a shared tree**, coalescing of concurrent misses with identical `(settings, language, units)` (one command), **nudge during an in-flight pull** (the stale result is served to its waiting callers but not cached; a request arriving after the nudge starts a new command; the cache ends on the post-nudge tree), invalidation on nudge / stop / restart / update / uninstall / successful action, nudge for an undeclared key ignored, rate limit 1 per 10 s per `(integration, key)`, `widget-updated` broadcast, **miss bounds** (3rd concurrent miss queued behind the 2 in flight; 31st miss in a minute → `429`).
- **Controllers** (supertest): widget list for a non-admin (widgets of a `device` integration visible with `integration_status` and nothing else operational, stopped integration listed with its status); ## Later leads

Each is its own capability file when it comes, additive to this one:

- a generic **integration event scene trigger** (the "new release" trigger of PR #3061, generalized: `external-integration.event` with declared event keys — the same mechanism serves "vacuum stuck" and "charge complete");
- **chip-sized widgets** (`size: "chip"` in the declaration, rendered in the chips bar);
- two focal components the field will likely ask for — a **`map`** (a vehicle's position; tiles served without leaking the user's IP is the design question) and a **`schedule`** (a heating program or charging plan by hour, which a bar chart only approximates);
- the acting **`user`** in `widget.action`;
- custom integration **pages** (topic 10760) reusing the same vocabulary outside the dashboard;
- AI-assisted dashboard composition on top of the published schema.

## Alternatives considered

- **Custom HTML / iframe / JS widgets**: rejected, the RFC's requirement (3) and the founding choice of topic 10641 — the core could guarantee none of theme, dark mode, responsiveness, translations or security.
- **One integration type per domain** (`movies`, then recipes, transport, sports…): rejected on PR #3061 — each type is a core surface (lib, pivot, widget, trigger, spec) maintained forever for one domain.
- **A `widget` type for widget-only integrations**: rejected (principle 6) — a type named after one capability breaks on the first integration combining two (a widget and a scene trigger, no device). `provider` names the shape, capabilities name the contract.
- **`type: "device"` with empty Devices/Discovery screens for widget-only integrations** (the first draft of this spec): rejected — a declaration that lies to the user (tabs that can never fill) and a device host-API surface the integration has no business with; hiding the tabs when no device is published would have been conditional UI covering a wrong declaration instead of fixing it.
- **Static layout in the manifest + data-binding expressions**: rejected (principle 2) — a template language to specify and maintain on two repos, for less expressiveness than a runtime tree. The manifest keeps what is static by nature: identity and settings.
- **Free composition** (dozens of components in integration-chosen order, long lists with internal scrolling): rejected (principle 3, section 5) — it is the Home Assistant clutter failure mode; the content budget and the canonical order keep every widget card-shaped without removing anything a domain widget legitimately needs.
- **Fixed widget sizes** (iOS small / medium / large declared in the manifest): considered as the alternative framing of the budget; rejected because a Gladys box fills its column and has a natural height — a size class would constrain the wrong axis. The budget constrains the content directly.
- **Push (`POST /widget/content`) instead of pull**: rejected — per-instance settings make a pushed payload ambiguous, memory would hold every variant, and the "trigger, not data" doctrine already gave the weather type sub-second freshness with a stateless nudge.
- **Core-side fetch of third-party image URLs**: rejected — an SSRF into the host network from a sandboxed container, and the core would carry the bytes anyway; the integration serves them on demand (B.18 point 6, generalized).
- **Layout containers (`row`, `columns`, nesting)**: rejected — the canonical slots and the auto-flow of tiles and buttons cover the stats banner and the button row with zero layout language; the dashboard spec rejected user-composed nestable stacks for the same reason, and an integration-composed one would have to look good in every theme and width just the same.
- **Free colors, sizes, fonts**: rejected — semantic `color` enum only; "beautiful by default" is the core's job.
- **Widget data bent into device features** (a "movie" sensor): rejected, the B.18 doctrine — a device feature is a controllable or measurable thing, not a transport for structured content.
- **Validating `settings` at dashboard save time**: rejected (section 2) — the render-time validation must exist anyway, and coupling `t_dashboard` writes to a manifest lookup buys nothing it does not already provide.

## Out of scope

- **Input controls** (sliders, selects, text fields, forms): a widget is read-and-tap. Setpoints, volumes and levels are device features, controlled through the core device widgets; the multi-step wizards of topic 10760 are a different surface with a different interaction model.
- Per-user widgets (content depending on who looks): a widget instance is per dashboard, and the acting user is not transmitted.
- Widgets from **internal** services: the mechanism is designed for the external contract; an internal service keeps writing a core box (it can change the core), and nothing prevents a later internal adapter exposing the same `widget.get` interface on the stateManager, exactly as `weather.get` is duck-typed today.
- Rich text of any kind (Markdown, HTML) inside a widget — line breaks in `body` are the formatting (C.1).
- Any change to the chips / quick-actions / house-view boxes: an integration widget is its own card; putting integration data in a chip is the lead above.
- Generic control widgets that other platforms offer and Gladys lacks (map, calendar, media control with seek and volume, thermostat card): core widget matters, tracked in `dashboard-flexible-layout-and-widgets.md`, not integration widgets.
