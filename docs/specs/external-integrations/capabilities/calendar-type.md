# B.19 "Calendar" type: generic calendar providers (phase 2, milestone 1 shipped — per-user OAuth2 in milestone 2)

Goal: that calendar providers — Google Calendar, Outlook/Microsoft 365, Nextcloud/Framagenda and other CalDAV servers beyond the internal client, and non-personal feeds (school timetables, waste collection, sports fixtures, public ICS calendars) — become ordinary external integrations, feeding the **same calendar view and the same scene triggers** as the internal CalDAV service, without the core knowing any provider by name (community request, topic 10432: "adapt the API to support external calendar-type integrations, like CalDAV internally today").

**Current state (verified in the code)** — consumption is already generic, production is not:

- **Consumption never names a service.** The calendar view reads the DB over `GET /api/v1/calendar` + `GET /api/v1/calendar/event` (`front/src/actions/calendar.js`); the scene trigger `calendar.event-is-coming` is evaluated every minute by a core cron against `t_calendar_event` (`scene.checkCalendarTriggers.js`), and the scene action `calendar.is-event-running` goes through `calendar.findCurrentlyRunningEvent` — both consider **`shared: true` calendars only** (`calendar.findCurrentlyRunningEvent.js:39`). Unlike weather (`getService('openweather')`) or messaging (`sendToUser` hardcoded), **no core refactor of the consumers is needed**: whatever writes `t_calendar`/`t_calendar_event` feeds everything.
- **Production is in-process only.** The CalDAV service is the single producer, and it never goes through HTTP: it calls `this.gladys.calendar.*` directly. The data model already carries everything an external producer needs: `t_calendar.service_id` (FK, cascade delete), a UNIQUE `external_id` on calendars (CalDAV stores the calendar URL) and on events (iCal UID, `UID + occurrence date` for expanded recurrences — `caldav/lib/calendar/calendar.formaters.js:98,148,215`), the per-calendar `sync` flag (user-owned: disabling empties the events and the service skips the calendar — `calendar.disableCalendar.js`), `color`, `shared`, `last_sync`.
- **What is missing** (established for this design): no calendar endpoint on the host API; no upsert primitive in `lib/calendar/` (CalDAV re-implements a get-then-create loop, `calendar.syncUserCalendars.js:167-185`); calendar and event selectors are slugified naively at creation (`addSelectorBeforeValidateHook`) instead of using `buildUniqueSelector` — two same-named calendars collide on the UNIQUE column with an unrecoverable `409`, the exact problem C.3 documents as solved for devices; the user calendar routes check no ownership (`calendar.update.js`/`destroy.js`/`*Event.js` operate by selector alone); `externalIntegration.uninstall.js` cleans devices and variables but not calendars (they would vanish through the FK cascade, silently and untested); no calendar WebSocket message exists, so the calendar view never refreshes in real time; `t_calendar.user_id` is NOT NULL while an integration JWT carries no user (B.3).

**Design principle: the integration syncs, the core stores.** The calendar type is a **push model** into `t_calendar`/`t_calendar_event` — the CalDAV pattern, not the weather pull: every consumer (view, minute-cron scene triggers) reads the DB on its own schedule, and a pull model would put an unaudited third-party container on the critical path of the scene scheduler. The integration owns the provider protocol, the credentials and the sync cadence (its own cron, in its container); the core owns storage, normalization, rendering and automations. **One-way mirror in v1**: Gladys never writes back to the provider — parity with the internal CalDAV client, which is read-only too; events created by hand in Gladys coexist with pushed ones and are never touched by a sync (see the prune rule below).

**1. Core prerequisites (beneficial even without external integrations)**:

- **Batch upsert primitives** in `lib/calendar/` keyed by `external_id` (`calendar.upsertCalendars(userId, serviceId, calendars)`, `calendar.upsertEvents(calendarId, events, window?)`), transactional, replacing caller-side get-then-create loops. The CalDAV service can migrate onto them later (out of scope of this workstream).
- **`buildUniqueSelector` for calendars and events** (`utils/addSelector.js:56-87`, the device mechanics of C.3): the readable slug when free, then `-2`, `-3`… Two users each pushing a "Personal" calendar must both succeed.
- **Ownership checks on the user calendar routes**: `PATCH`/`DELETE /api/v1/calendar/:selector` and the event routes currently let any authenticated user edit any calendar — to fix before an ecosystem multiplies calendars. A user acts on their own calendars (plus shared ones for reads, as today).
- **Explicit cleanup at uninstall**: destroy the service's calendars (all users) before the `t_service` row, added to the B.2 uninstall contract and tested — never rely on the silent FK cascade.
- **Real-time refresh**: new `WEBSOCKET_MESSAGE_TYPES.CALENDAR.UPDATED` (`calendar.updated { "calendar_selectors": [...] }`), pushed to the owning user — to everyone when the calendar is shared — after any write batch; the calendar view refetches its displayed range on it.
- **Drive-bys**: a `CALENDAR_TYPES` constant (`CALDAV`, `WEBCAL`, `EXTERNAL`) replacing today's free strings in `t_calendar.type`; fix the double `calendar.associate` definition (`server/models/calendar.js` — the second erases the first, so `hasMany(CalendarEvent)` is never registered); guard the frontend color join (`front/src/actions/calendar.js:22`: `.find()` on a missing calendar returns `undefined` → TypeError).

**2. Per-user accounts — who owns a pushed calendar.** `t_calendar.user_id` is NOT NULL and the integration JWT is tied to no user, so every push must resolve a user — and should: calendars are personal data, and the internal CalDAV precedent is per-user (each user configures their account, owns their calendars, opts into sharing). The model generalizes B.15's per-user machinery:

- **Manifest**: `type: "calendar"` + optional **`account_schema`** — same flat format, validation and rendering engine as the `config_schema` (C.1) and B.15's `contact_schema`, values stored in `t_variable` scoped `(service_id, user_id)`. Same restrictions as `contact_schema`: `{{port:<name>}}` refused; **`oauth2` and `account_link` refused in milestone 1** (the Connect relay is integration-scoped — see milestone 2 below). The admin-level `config_schema` remains available for shared provider settings (server URL, the OAuth app's client_id/secret…). No Devices/Discovery screens: like communication and weather, the generic page branches by type.
- **Per-user activation is the consent gesture.** The generic page shows **every user** (not only admins) a "**My calendars**" block: the `account_schema` fields (their values) and an Enable action; once enabled, the list of **their** calendars pushed by the integration, each with its **`sync`** and **`shared`** toggles, and a Disable action that **destroys their calendars** (explicit confirmation). An integration with nothing to ask per user (a public feed) simply declares no `account_schema`: the block still renders (no fields, just the Enable/Disable action), and enabling remains the per-user gesture — enabling = consenting to calendars appearing in your view; a household-wide calendar is obtained by sharing it (`shared`), the existing model. Enablement is materialized by a reserved `(service_id, user_id)` variable (`EXTERNAL_INTEGRATION_CALENDAR_ACCOUNT`, the B.15 `CONTACT_VARIABLE` pattern), so "enabled with zero fields" is a first-class state, not an empty-config edge case.
- **Non-admin visibility**: like communication integrations — an installed calendar integration appears in a non-admin's catalog (under its browse categories, never the store) and its page shows them only the per-user block; supervision, config, actions, logs stay admin-only. The C.5 reduced view extends to the calendar type.
- **Authority note — `shared` is the automation boundary.** The scene trigger and action only see `shared: true` calendars (verified above). A pushed calendar can therefore fire scenes only after the user shares it: two explicit gestures (enable the integration, then share the calendar) sit between an unaudited container and the scene engine. The share toggle's help text says so ("a shared calendar is visible to the whole household and can trigger scenes").

**3. Host API** — all endpoints below require `type: "calendar"` in the manifest (`403 FORBIDDEN` otherwise, the B.15 gate pattern), tenant isolation by the JWT as everywhere (an integration only ever sees or writes rows whose `service_id` is its own). **Identifiers are user-scoped**: `t_calendar.external_id` and `t_calendar_event.external_id` are globally UNIQUE columns, so the C.2 prefix is extended for the calendar surface — every calendar and event `external_id` must start with **`ext:<selector>:<user_selector>:`** (the target user's selector — for events, the owning calendar's user; `400` otherwise, enforced server-side). Two household members syncing the same provider-side id (a Google "primary", the same public ICS feed, the same event UID) therefore can never collide or steal each other's rows: their ids differ by construction.

| Endpoint | Contract |
|---|---|
| `GET /api/integration/v1/calendar/account` | → `200 [ { "user": { "selector", "first_name", "language" }, "config": { ... } } ]` — the users who **enabled** the integration, with their `account_schema` values, secrets included (integration-side, like `GET /config`) |
| `GET /api/integration/v1/calendar?user=<selector>` | → `200 [ { "user", "external_id", "selector", "name", "description", "color", "sync", "shared" } ]` — the integration's calendars; `user` optional (absent = all enabled users, the startup resync in one call). `sync: false` tells the integration to **skip** that calendar |
| `POST /api/integration/v1/calendar` | `{ "user": "<selector>", "calendars": [ { "external_id", "name", "description"?, "color"? } ] }` → `200 { "success": true, "created": n, "updated": n }` — **upsert by `external_id`** (≤ 50 calendars per user, `400` beyond); creation stamps `type: EXTERNAL`, `sync: true`, `shared: false`; republication updates the integration-owned fields only (see point 5). User unknown or not enabled → `404` |
| `DELETE /api/integration/v1/calendar?external_id=...` | → `200 { "success": true }` — destroys the calendar and its events (its own calendars only, `404` otherwise); how a provider-side deletion propagates |
| `POST /api/integration/v1/calendar/event` | `{ "calendar_external_id", "window"?: { "from", "to" }, "events": [ ... ] }` → `200 { "success": true, "created": n, "updated": n, "deleted": n }` — **upsert by `external_id`**, ≤ 500 events per request; with `window`, prunes (point 5). Calendar unknown or another integration's → `404`; `sync: false` → `403` |

Rate limit: **30 calendar write requests (POST/DELETE) per minute per integration**, `429` beyond (the SQLite anti-spam sizing of `POST /state`); a full push of a 2000-event calendar is 4 requests. Example:

```json
POST /api/integration/v1/calendar/event
{
  "calendar_external_id": "ext:john-gcal:pepper:primary",
  "window": { "from": "2026-08-01T00:00:00.000Z", "to": "2026-09-01T00:00:00.000Z" },
  "events": [
    {
      "external_id": "ext:john-gcal:pepper:8f3a@google.com",
      "name": "Dentist",
      "start": "2026-08-14T09:00:00.000Z",
      "end": "2026-08-14T09:30:00.000Z",
      "location": "12 rue des Lilas, Paris",
      "url": "https://calendar.google.com/event?eid=..."
    },
    {
      "external_id": "ext:john-gcal:pepper:holiday-20260815",
      "name": "Assomption",
      "start": "2026-08-15T00:00:00.000Z",
      "end": "2026-08-16T00:00:00.000Z",
      "full_day": true
    }
  ]
}
```

**4. Normalization and bounds** (`normalizeWeather` transposed — the payload is never trusted): whitelist of fields, anything unknown dropped. Calendar: `name` required 1–100 chars, `description` ≤ 500 (stored as `""` when absent — the column is NOT NULL), `color` matching `^#[0-9a-f]{6}$` (invalid → dropped; absent → the core stamps the CalDAV default `#3174ad`). Event: `external_id` required (user-scoped prefix enforced, ≤ 255) — a **stable per-user event identity, independent of the calendar**: the provider UID after the `ext:<selector>:<user>:` prefix is the natural choice, as in the example. Because the id is calendar-independent, an event republished under another calendar **of the same user** is **moved** (the upsert finds the row by `external_id` and updates its `calendar_id`). An integration that instead embeds the calendar in its event ids renounces moves: a provider-side move then surfaces as a new id, the old row leaving through the window prune or an explicit republication — a consequence of that id choice, not a protocol behavior. `name` required 1–200, `start` required (ISO 8601, parsed and validated), `end` optional but ≥ `start` (violation → `400` naming the entry), `full_day` strict boolean default `false` (full-day events are interpreted by calendar date, `end` exclusive — the iCalendar `DTEND` convention), `location` ≤ 500, `description` ≤ 1000, `url` http(s) ≤ 500. Hard cap: **≤ 10 000 events per calendar** (`400` on the upsert that would exceed it). **Recurrences are expanded by the integration** — the CalDAV precedent (`external_id` = UID + occurrence date): the core stores materialized occurrences only and embeds no RRULE engine; a bounded horizon (12 months ahead recommended) keeps expansion under the caps.

**5. Sync semantics — who owns which field, who deletes what.**

- **Field ownership**: `name`, `description`, `color` are integration-owned (overwritten by every push); `sync`, `shared`, `selector` are user-owned (never touched by a push) — the CalDAV split (`delete formatedCalendar.sync`, `calendar.syncUserCalendars.js:96`). A user's manual edit of an integration-owned field lasts until the next push, as with CalDAV today.
- **Window prune** — deletions without bookkeeping: with `window: { from, to }`, membership is by **overlap**, not by start — an event overlaps the window when `start < to` and, when `end` is set, `end > from` (**exclusive end**, the same convention as full-day `DTEND`: a full-day event ending exactly at `from` belongs to the previous window, and a rolling monthly window at midnight UTC does not over-include the previous day), else `start ≥ from` — so a multi-day event straddling `from` stays updatable and prunable like any other. Events of that calendar overlapping the window, whose `external_id` carries the integration's prefix, and which are absent from the pushed list are **deleted** — a provider-side deletion propagates by simply republishing the window, idempotently. Events created by hand in Gladys (unprefixed `external_id`) are **never pruned**. Every pushed event must overlap the window (`400` otherwise — keeps the replace semantics crisp). Without `window`: pure upsert, no deletion.
- **`sync` toggled off** (user gesture): the core **empties the calendar's events** (the CalDAV `disableCalendar` semantics) and further event pushes to it answer `403`; toggled back on, the integration's next full-window republication restores everything — idempotence makes re-enabling free.
- **Account disabled**: the user's calendars of this integration are destroyed (explicit confirmation in the UI). **Uninstall**: every calendar of the service is destroyed, all users (point 1's explicit cleanup).
- **Both sides are notified of every change**: the frontend via `calendar.updated` (point 1), the integration via `external-integration.calendar.account-updated { "user" }` (C.4) on enable/disable/account-value change/`sync` or `shared` toggle — fire-and-forget, no queue: on every (re)connection a calendar integration re-reads `GET /calendar/account` + `GET /calendar` and adjusts its sync loops (the C.4 resync contract, extended to the calendar surface). On a **state transition, the frontend push targets the union of previous and new visibility** — the steady-state recipient rule alone would leave stale views: unsharing (`shared` true→false) still pushes to everyone one last time so previous viewers drop the calendar, an event move includes the **source** calendar's selector next to the destination's (everyone when either is shared), and the deletions of an account disable and of an uninstall push the removed selectors to their previous viewers.
- **Privacy — one-way by construction**: the host API exposes to the integration only its **own** `service_id` rows. It can never read the user's other calendars (CalDAV's, manual ones, another integration's) nor their events: the calendar surface is a write-path plus its own state, nothing else. The install screen states the capability ("this integration will be able to create calendars and events in Gladys, for the users who enable it").

**Management API (frontend ↔ server)** — per-user routes under the existing prefix, standard user auth, each user acting on **their own** account and calendars only (`404` on anything else, including another user's calendar — indistinguishable from an unknown selector):

| Method & route | Body → Response |
|---|---|
| `GET /api/v1/external_integration/:selector/calendar/account` *(any user)* | → `{ "enabled", "config": { ...secrets null }, "configured_secrets": [...], "calendars": [ { "selector", "name", "color", "sync", "shared" } ] }` — the requesting user's view |
| `POST .../:selector/calendar/account` *(any user)* | `{ "config": {...} }` validated against the `account_schema` (`422` otherwise; without an `account_schema`, `config` must be `{}` or omitted, any key → `422`) → `200` — enables the integration for the requesting user (idempotent; also how account values are edited) + `calendar.account-updated` push |
| `DELETE .../:selector/calendar/account` *(any user)* | → `200 { "success": true }` — disables and **destroys the user's calendars** of this integration (explicit UI confirmation) + push |
| `PATCH .../:selector/calendar/:calendar_selector` *(any user)* | `{ "sync"?, "shared"? }` — these two keys only; `sync: false` empties the events (see point 5) → `200` + pushes to the frontend and the integration |

Account enablement and values are stored per `(service_id, user_id)` variables (the B.15 `CONTACT_VARIABLE` pattern — no migration).

**6. Milestone 2 — per-user OAuth2 (the Google Calendar / Outlook gate).** Milestone 1 covers every provider whose per-user identity fits `account_schema` fields: CalDAV servers and Nextcloud/Framagenda (app passwords), iCloud (app-specific passwords), token-based APIs, public ICS feeds (no account at all). Google and Microsoft only speak per-user OAuth, which the current `oauth2` machinery (C.1) cannot express — it is admin-scoped and config-level. Sketch, to be detailed when the milestone starts: allow `oauth2` fields in `account_schema`; open the two oauth relay routes (C.5) to the authenticated user when the `key` belongs to the `account_schema` (admin stays required for `config_schema` keys); the WS relays `oauth.get-authorize-url`/`oauth.callback` gain a `user: { "selector" }` field; per-user token storage via a per-user variant of the free config storage (`POST /api/integration/v1/calendar/account/config { "user", "config" }` — keys outside the schema, never shown in the UI, returned by `GET /calendar/account`); a per-user connection state surfaces in the "My calendars" block. Nothing in milestone 1 closes these doors: account payloads already carry the user selector, `(service_id, user_id)` storage exists, and the oauth relay machinery is user-agnostic except for its route guard.

**Frontend**: the catalog does not key its shelves on the manifest `type` (browse categories, `integration-catalog-categories.md`): a `type: "calendar"` integration is listed under the `categories` of its store index entry (its manifest field, else the indexer's fallback mapping — the `services` shelf, where the native CalDAV entry of `front/src/config/integrations/calendars.json` lives), with the external badge and status like everywhere; `type` stays the technical key of the role rule (non-admin visibility above) and of the screens. Required front changes — every `hasDeviceScreens`-style gate, not only the page chrome: the non-admin installed filter and `getInstalledUrl` (`front/src/routes/integration/index.js`) gain `'calendar'` (any other type falls back to `'device'`), and the `['communication','weather']` exclusion sets gain `'calendar'` in `ExternalIntegrationPage` (tabs), `install-page` (post-install redirect), and the `discover-page`/`device-page` guards (redirect to the Configuration screen when reached by URL). The generic page gains the "My calendars" block (point 2); the calendar view gains the `calendar.updated` listener (point 1) — no other view change: pushed calendars render exactly like CalDAV ones.

**7. Contracts owned by this file** (the shared `contracts/` tables carry the v1 core surface only — see `contracts/conventions.md`; the manifest field, the host API endpoints of point 3 and the management routes of point 5 above complete this list).

*WebSocket messages* (C.4 envelope and conventions):

| Direction | `type` | `payload` |
|---|---|---|
| core → integration | `external-integration.calendar.account-updated` | `{ "user": "<user_selector>" }` — a user enabled or disabled the integration, changed their account values, or toggled a calendar's `sync`/`shared`; no `message_id`, no ack (the `config-updated` family), emitted **after** the core applied the change (on a disable, the user's calendars are already destroyed); the integration re-reads `GET /calendar/account` and `GET /calendar` and adjusts its sync loops |
| core → frontend | `calendar.updated` | `{ "calendar_selectors": [...] }` — on the existing user WS, pushed after any calendar/event write batch — to the owning user, to every connected user when the calendar is `shared` (union of previous and new visibility on a transition, point 5) — so the calendar view refetches its displayed range; deliberately in the core `calendar` namespace, not `external-integration.*`: it belongs to the core calendar domain and the internal CalDAV service can adopt it too |

The C.4 **resync contract** extends to the calendar surface: on every (re)connection, a calendar integration additionally re-reads `GET /calendar/account` + `GET /calendar` (core→integration messages emitted during a disconnection are lost, `account-updated` included).

**Tests** (monorepo, in addition to the framework checks of `core/tests.md`): manifest `type: "calendar"` accepted, `account_schema` validated like `contact_schema` (`oauth2`, `account_link` and `{{port:<name>}}` refused in milestone 1); host-API gate (`403` on every calendar endpoint for the other types); per-user account routes (`account_schema` validation → `422`, enable idempotent, disable destroys the requesting user's calendars only, per-user isolation: another user's account or calendar → `404`); upsert idempotence (same push twice → zero writes), selector collision (two users, two same-named calendars → `buildUniqueSelector`), field ownership on republication (`sync`/`shared`/`selector` untouched, `name`/`description`/`color` overwritten), window prune by overlap (integration-prefixed absent events deleted including a multi-day event straddling `from`, manual unprefixed events preserved, event not overlapping the window → `400`, exclusive end bound: an event ending exactly at `from` does not overlap), event move (same `external_id` republished under another calendar of the same user → `calendar_id` updated, no duplicate row, source **and** destination selectors in the `calendar.updated` push, the 10 000 cap enforced on the move path too), transition pushes (unshare → one last send-all, uninstall → removed selectors pushed to their previous viewers), normalization bounds (counts and caps, lengths, invalid `color` dropped, `end` < `start` → `400`, 10 000-events-per-calendar cap), rate limit → `429`, tenant and user isolation (A's token cannot write B's calendars, `external_id` without the `ext:<selector>:<user>:` prefix → `400`), push on a `sync: false` calendar → `403` and events emptied on the toggle, explicit uninstall cleanup (no reliance on the FK cascade), WS pushes (`calendar.updated` to the right users, `calendar.account-updated` to the integration), and a CalDAV regression pass (its sync loops untouched by the new primitives until it migrates).

**What v1 anticipated (and it holds)**: extensible manifest `type` + catalog filter, WS `<domain>.<action>` convention, per-user `(service_id, user_id)` variables and per-user blocks (B.15), server-side-enforced authorization gates, the normalize-and-bound doctrine (B.18). Phase 3: migrate the internal CalDAV loops onto the point-1 upsert primitives, then — the B.15/B.18 path — a community-maintained external CalDAV/Google/Outlook equivalent may deprecate the internal service.
