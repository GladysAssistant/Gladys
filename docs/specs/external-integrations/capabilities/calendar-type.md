# "Calendar" type: generic calendar providers (phase 2 — milestone 1 shipped, per-user OAuth2 in milestone 2)

Goal: that calendar providers — Google Calendar, Outlook/Microsoft 365, Nextcloud/Framagenda and other CalDAV servers beyond the internal client, and non-personal feeds (school timetables, waste collection, sports fixtures, public ICS calendars) — become ordinary external integrations, feeding the **same calendar view and the same scene triggers** as the internal CalDAV service, without the core knowing any provider by name (community request, topic 10432: "adapt the API to support external calendar-type integrations, like CalDAV internally today").

This file has no historic section identifier (the README's rule: none is allocated to a new file) — it is cited by its path, `capabilities/calendar-type.md`.

**State before this workstream (verified in the code at the time)** — consumption was already generic, production was not:

- **Consumption never names a service.** The calendar view reads the DB over `GET /api/v1/calendar` + `GET /api/v1/calendar/event` (`front/src/actions/calendar.js`); the scene trigger `calendar.event-is-coming` is evaluated every minute by a core cron against `t_calendar_event` (`scene.checkCalendarTriggers.js`), the scene actions `calendar.is-event-running` and `calendar.get-events` go through `calendar.findCurrentlyRunningEvent` / `calendar.findEventsInRange` — all of them consider **`shared: true` calendars only** (`'$calendar.shared$': true` in the three queries) — and the dashboard chips box and the MCP calendar tool read the same tables. Unlike weather (`getService('openweather')`) or messaging (`sendToUser` hardcoded), **no core refactor of the consumers was needed**: whatever writes `t_calendar`/`t_calendar_event` feeds everything.
- **Production was in-process only.** The CalDAV service is the single internal producer, and it never goes through HTTP: it calls `this.gladys.calendar.*` directly. The data model already carried everything an external producer needs: `t_calendar.service_id` (FK, cascade delete), a globally UNIQUE `external_id` on calendars (CalDAV stores the calendar URL) and on events (iCal UID, `UID + occurrence date` for expanded recurrences — `caldav/lib/calendar/calendar.formaters.js`), the per-calendar `sync` flag (user-owned: disabling empties the events and the service skips the calendar — `calendar.disableCalendar.js`), `color`, `shared`, `last_sync`.
- **What was missing**, and what point 1 below added: no calendar endpoint on the host API; no upsert primitive in `lib/calendar/` (CalDAV re-implements a get-then-create loop in `calendar.syncUserCalendars.js`); calendar and event selectors slugified naively at creation (`addSelectorBeforeValidateHook`) instead of `buildUniqueSelector` — two same-named calendars collided on the UNIQUE column with an unrecoverable `409`, the exact problem C.3 documents as solved for devices; no ownership check on the user calendar routes (`calendar.update.js`/`destroy.js`/`*Event.js` operated by selector alone, and the update routes mass-assigned the body); `externalIntegration.uninstall.js` cleaned devices and variables but not calendars; no calendar WebSocket message, so the calendar view never refreshed in real time; `t_calendar.user_id` NOT NULL while an integration JWT carries no user (B.3).

**Design principle: the integration syncs, the core stores.** The calendar type is a **push model** into `t_calendar`/`t_calendar_event` — the CalDAV pattern, not the weather pull: every consumer (view, minute-cron scene triggers) reads the DB on its own schedule, and a pull model would put an unaudited third-party container on the critical path of the scene scheduler. The integration owns the provider protocol, the credentials and the sync cadence (its own cron, in its container); the core owns storage, normalization, rendering and automations. **One-way mirror in v1**: Gladys never writes back to the provider — parity with the internal CalDAV client, which is read-only too; events created by hand in Gladys coexist with pushed ones and are never touched by a sync (see the prune rule below).

**Why a type and not a capability field.** `capabilities/provider-type.md` sets the bar for a new `type`: *a generic pivot interface the core itself consumes (dashboard, assistant, scenes), never a domain* — anything else is a capability field usable by every type. Calendar passes it the way `weather` did: the pivot is the core calendar store (`t_calendar`/`t_calendar_event`, normalized and bounded on entry, point 4), and the core consumes it on its own through the calendar view, the chips box, the calendar scene trigger and actions and the MCP calendar tool — the integration never renders nor evaluates anything. The type also carries what a field could not: a host-API surface gated on it (point 3), per-user accounts with their own consent gesture (point 2), and a screen set without Devices/Discovery. A calendar integration may still declare capability fields on top (a widget, a scene trigger), like any type.

**1. Core prerequisites (beneficial even without external integrations)**:

- **Batch upsert primitives** in `lib/calendar/` keyed by `external_id` (`calendar.upsertCalendars(userId, serviceId, calendars)`, `calendar.upsertEvents(calendarId, events, { window, prunePrefix })`), transactional, replacing caller-side get-then-create loops. A row found under another owner (another user or another service) is **never stolen**: the upsert fails with `409` instead. The CalDAV service can migrate onto them later (out of scope of this workstream).
- **`buildUniqueSelector` for calendars and events** created by the upserts (`utils/addSelector.js`, the device mechanics of C.3): the readable slug when free, then `-2`, `-3`… Two users each pushing a "Personal" calendar both succeed.
- **Ownership checks on the user calendar routes**: `PATCH`/`DELETE /api/v1/calendar/:selector`, `POST /api/v1/calendar/:selector/event` and `PATCH`/`DELETE /api/v1/calendar/event/:selector` act on the requesting user's **own** calendars only (another user's answers `404`, like an unknown selector); the two update routes write a **whitelist** of user-editable fields (calendar: `name`, `description`, `color`, `sync`, `shared`, `notify`; event: `name`, `start`, `end`, `full_day`, `location`, `description`, `url`) — the ownership columns (`user_id`, `service_id`, `calendar_id`, `selector`, `external_id`) are out of reach, so owning a calendar or an event is never a way to hand it over. Internal callers (the CalDAV sync) pass no user and keep writing full rows. Reads are unchanged (own calendars plus shared ones).
- **Reserved `ext:` namespace**: the user-scoped identifiers of point 3 are only collision-free if nobody else can take them. `POST /api/v1/calendar` and the user event creation route refuse an `external_id` starting with `ext:` (`400`) — otherwise a household member could create a calendar or an event under the id another member's integration will push, and make that member's sync fail with `409` on a row they do not own.
- **Explicit cleanup at uninstall**: destroy the service's calendars (all users) before the `t_service` row, added to the B.2 uninstall contract and tested — never rely on the silent FK cascade.
- **Real-time refresh**: new `WEBSOCKET_MESSAGE_TYPES.CALENDAR.UPDATED` (`calendar.updated { "calendar_selectors": [...] }`), pushed after any write batch, **each calendar to its own audience**: a shared calendar to every connected user, a private one to its owner only — a batch mixing both is split in two pushes, never broadcast whole (a single broadcast would leak the selectors, i.e. the slugified names, of private calendars to the household). The calendar view refetches its displayed range on it.
- **Drive-bys**: a `CALENDAR_TYPES` constant (`CALDAV`, `WEBCAL`, `EXTERNAL`) replacing the free strings in `t_calendar.type`; the double `calendar.associate` definition fixed (`server/models/calendar.js` — the second erased the first, so `hasMany(CalendarEvent)` was never registered); the frontend color join guarded (`front/src/actions/calendar.js`: `.find()` on a missing calendar returned `undefined` → TypeError), and an event without `end` rendered at its `start` instead of 1970.

**2. Per-user accounts — who owns a pushed calendar.** `t_calendar.user_id` is NOT NULL and the integration JWT is tied to no user, so every push must resolve a user — and should: calendars are personal data, and the internal CalDAV precedent is per-user (each user configures their account, owns their calendars, opts into sharing). The model generalizes B.15's per-user machinery:

- **Manifest**: `type: "calendar"` + optional **`account_schema`** — same flat format, validation and rendering engine as the `config_schema` (C.1) and B.15's `contact_schema`, values stored in `t_variable` scoped `(service_id, user_id)`. Same restrictions as `contact_schema`: `{{port:<name>}}` refused; **`oauth2` and `account_link` refused in milestone 1** (the Connect relay is integration-scoped — see milestone 2 below); `account_schema` on any other type is refused. The admin-level `config_schema` remains available for shared provider settings (server URL, the OAuth app's client_id/secret…). No Devices/Discovery screens: like communication, weather and provider, the generic page branches by type.
- **Per-user activation is the consent gesture.** The generic page shows **every user** (not only admins) a "**My calendars**" block: the `account_schema` fields (their values, secrets never echoed back) and an Enable action; once enabled, the list of **their** calendars pushed by the integration, each with its **`sync`** and **`shared`** toggles, and a Disable action that **destroys their calendars** (explicit inline confirmation). An integration with nothing to ask per user (a public feed) simply declares no `account_schema`: the block still renders (no fields, just the Enable/Disable action), and enabling remains the per-user gesture — enabling = consenting to calendars appearing in your view; a household-wide calendar is obtained by sharing it (`shared`), the existing model. Enablement is materialized by a reserved `(service_id, user_id)` variable (`EXTERNAL_INTEGRATION_CALENDAR_ACCOUNT`, the B.15 `CONTACT_PROFILE` pattern), so "enabled with zero fields" is a first-class state, not an empty-config edge case.
- **Non-admin visibility**: like communication integrations — an installed calendar integration appears in a non-admin's catalog (under its browse categories, never the store) and its page shows them only the per-user block; supervision, config, actions, logs stay admin-only. The C.5 reduced view extends to the calendar type.
- **Authority note — `shared` is the automation boundary.** The scene trigger and actions only see `shared: true` calendars (see above). A pushed calendar can therefore fire scenes only after the user shares it: two explicit gestures (enable the integration, then share the calendar) sit between an unaudited container and the scene engine. The share toggle's help text says so ("a shared calendar is visible to the whole household and can trigger scenes").

**3. Host API** — all endpoints below require `type: "calendar"` in the manifest (`403 FORBIDDEN` otherwise, the B.15 gate pattern), tenant isolation by the JWT as everywhere (an integration only ever sees or writes rows whose `service_id` is its own). **Identifiers are user-scoped**: `t_calendar.external_id` and `t_calendar_event.external_id` are globally UNIQUE columns, so the C.2 prefix is extended for the calendar surface — every calendar and event `external_id` must start with **`ext:<selector>:<user_selector>:`** (the target user's selector — for events, the owning calendar's user; `400` otherwise, enforced server-side) and is at most 255 characters. Two household members syncing the same provider-side id (a Google "primary", the same public ICS feed, the same event UID) therefore never collide nor steal each other's rows: their ids differ by construction, and the `ext:` namespace is reserved to the integrations (point 1).

| Endpoint | Contract |
|---|---|
| `GET /api/integration/v1/calendar/account` | → `200 [ { "user": { "selector", "first_name", "language" }, "config": { ... } } ]` — the users who **enabled** the integration, with their `account_schema` values, secrets included (integration-side, like `GET /config`) |
| `GET /api/integration/v1/calendar?user=<selector>` | → `200 [ { "user", "external_id", "selector", "name", "description", "color", "sync", "shared" } ]` — the integration's calendars; `user` optional (absent = every user's, the startup resync in one call); a non-string `user` → `400`. `sync: false` tells the integration to **skip** that calendar |
| `POST /api/integration/v1/calendar` | `{ "user": "<selector>", "calendars": [ { "external_id", "name", "description"?, "color"? } ] }` → `200 { "success": true, "created": n, "updated": n }` — **upsert by `external_id`** (≤ 50 calendars per user counting the existing ones, `400` beyond; a duplicate `external_id` in the batch → `400`); creation stamps `type: EXTERNAL`, `sync: true`, `shared: false`; republication updates the integration-owned fields only (point 5). User unknown or not enabled → `404` (indistinguishable) |
| `DELETE /api/integration/v1/calendar?external_id=...` | → `200 { "success": true }` — destroys the calendar and its events (its own calendars only, `404` otherwise); how a provider-side deletion propagates |
| `POST /api/integration/v1/calendar/event` | `{ "calendar_external_id", "window"?: { "from", "to" }, "events": [ ... ] }` → `200 { "success": true, "created": n, "updated": n, "deleted": n }` — **upsert by `external_id`**, ≤ 500 events per request, a duplicate `external_id` in the batch → `400`; with `window` (`from` < `to`, both ISO 8601), prunes (point 5). Calendar unknown or another integration's → `404`; `sync: false` → `403` |

Rate limit: **30 calendar write requests (POST/DELETE) per minute per integration**, `429` beyond (the SQLite anti-spam sizing of `POST /state`, fixed one-minute window in memory, reset at uninstall); a full push of a 2000-event calendar is 4 requests. Example:

```json
POST /api/integration/v1/calendar/event
{
  "calendar_external_id": "ext:john-gcal:pepper:primary",
  "window": { "from": "2026-08-01T00:00:00.000Z", "to": "2026-09-01T00:00:00.000Z" },
  "events": [
    {
      "external_id": "ext:john-gcal:pepper:8f3a@google.com",
      "name": "Dentist",
      "start": "2026-08-14T09:00:00.000Z",
      "end": "2026-08-14T09:30:00.000Z",
      "location": "12 rue des Lilas, Paris",
      "url": "https://calendar.google.com/event?eid=..."
    },
    {
      "external_id": "ext:john-gcal:pepper:holiday-20260815",
      "name": "Assomption",
      "start": "2026-08-15T00:00:00.000Z",
      "end": "2026-08-16T00:00:00.000Z",
      "full_day": true
    }
  ]
}
```

**4. Normalization and bounds** (`normalizeWeather` transposed — the payload is never trusted): whitelist of fields, anything unknown dropped. Calendar: `name` required 1–100 chars, `description` ≤ 500 (stored as `""` on creation when absent — the column is NOT NULL), `color` matching `^#[0-9a-f]{6}$` after lowercasing (invalid → dropped; absent on creation → the core stamps the CalDAV default `#3174ad`). Event: `external_id` required (user-scoped prefix enforced, ≤ 255) — a **stable per-user event identity, independent of the calendar**: the provider UID after the `ext:<selector>:<user>:` prefix is the natural choice, as in the example. Because the id is calendar-independent, an event republished under another calendar **of the same user and the same integration** is **moved** (the upsert finds the row by `external_id` and updates its `calendar_id`). An integration that instead embeds the calendar in its event ids renounces moves: a provider-side move then surfaces as a new id, the old row leaving through the window prune or an explicit republication — a consequence of that id choice, not a protocol behavior. `name` required 1–200, `start` required (a date string, parsed and validated), `end` optional but ≥ `start` (violation → `400` naming the entry), `full_day` strict boolean default `false` (full-day events are interpreted by calendar date, `end` exclusive — the iCalendar `DTEND` convention), `location` ≤ 500, `description` ≤ 1000, `url` http(s) ≤ 500. Hard cap: **≤ 10 000 events per calendar**, measured on the calendar the request produces — after the window prune, moves in included (`400` on the upsert that would exceed it). **Recurrences are expanded by the integration** — the CalDAV precedent (`external_id` = UID + occurrence date): the core stores materialized occurrences only and embeds no RRULE engine; a bounded horizon (12 months ahead recommended) keeps expansion under the caps.

**5. Sync semantics — who owns which field, who deletes what.**

- **Field ownership**: `name`, `description`, `color` are integration-owned (overwritten by every push that carries them — an absent `description` or an absent/invalid `color` keeps the stored value); `sync`, `shared`, `selector` are user-owned (never touched by a push) — the CalDAV split (`delete formatedCalendar.sync` in `calendar.syncUserCalendars.js`). A user's manual edit of an integration-owned field lasts until the next push, as with CalDAV today.
- **Window prune** — deletions without bookkeeping: with `window: { from, to }`, membership is by **overlap**, not by start — an event overlaps the window when `start < to` and, when `end` is set, `end > from` (**exclusive end**, the same convention as full-day `DTEND`: a full-day event ending exactly at `from` belongs to the previous window, and a rolling monthly window at midnight UTC does not over-include the previous day), else `start ≥ from` — so a multi-day event straddling `from` stays updatable and prunable like any other. Events of that calendar overlapping the window, whose `external_id` carries the integration's user-scoped prefix, and which are absent from the pushed list are **deleted** — a provider-side deletion propagates by simply republishing the window, idempotently. Events created by hand in Gladys (no `ext:` id — point 1 keeps it that way) are **never pruned**. Every pushed event must overlap the window (`400` otherwise — keeps the replace semantics crisp). The prune runs **before** the upsert, in the same transaction (same final state: the pushed ids are never pruned), which is what makes the events cap apply to the resulting calendar. Without `window`: pure upsert, no deletion.
- **`sync` toggled off** (user gesture): the core **empties the calendar's events** (the CalDAV `disableCalendar` semantics) and further event pushes to it answer `403`; toggled back on, the integration's next full-window republication restores everything — idempotence makes re-enabling free.
- **Account disabled**: the user's calendars of this integration are destroyed (explicit confirmation in the UI), events with them. **Uninstall**: every calendar of the service is destroyed, all users (point 1's explicit cleanup).
- **Both sides are notified of every change**: the frontend via `calendar.updated` (point 1), the integration via `external-integration.calendar.account-updated { "user" }` (C.4 envelope) on enable/disable/account-value change/`sync` or `shared` toggle — fire-and-forget, no queue: on every (re)connection a calendar integration re-reads `GET /calendar/account` + `GET /calendar` and adjusts its sync loops (the C.4 resync contract, extended to the calendar surface). On a **state transition, the frontend push targets the union of previous and new visibility**, each calendar to its own audience: unsharing (`shared` true→false) still pushes to everyone one last time so previous viewers drop the calendar; an event move pushes the **source** calendar's selector next to the destination's, each to its audience (a shared source to everyone, a private destination to its owner); the deletions of an account disable and of an uninstall push the removed selectors to their previous viewers.
- **Privacy — one-way by construction**: the host API exposes to the integration only its **own** `service_id` rows. It can never read the user's other calendars (CalDAV's, manual ones, another integration's) nor their events: the calendar surface is a write-path plus its own state, nothing else. The install screen states the capability ("this integration will be able to create calendars and events in Gladys, for the users who enable it").

**Management API (frontend ↔ server)** — per-user routes under the existing prefix, standard user auth, each user acting on **their own** account and calendars only (`404` on anything else, including another user's calendar — indistinguishable from an unknown selector; a non-calendar integration answers like an unknown selector too):

| Method & route | Body → Response |
|---|---|
| `GET /api/v1/external_integration/:selector/calendar/account` *(any user)* | → `{ "enabled", "config": { ...secrets null }, "configured_secrets": [...], "calendars": [ { "selector", "name", "color", "sync", "shared" } ] }` — the requesting user's view |
| `POST .../:selector/calendar/account` *(any user)* | `{ "config": {...} }` validated against the `account_schema` (partial merge, a secret set to `null` means unchanged; unknown key or invalid value → `422`; without an `account_schema`, `config` must be `{}` or omitted, any key → `422`) → `200` the view above — enables the integration for the requesting user (idempotent; also how account values are edited) + `calendar.account-updated` push |
| `DELETE .../:selector/calendar/account` *(any user)* | → `200 { "success": true }` — disables and **destroys the user's calendars** of this integration (explicit UI confirmation) + pushes |
| `PATCH .../:selector/calendar/:calendar_selector` *(any user)* | `{ "sync"?, "shared"? }` — these two keys only, strict booleans (`400` otherwise); `sync: false` empties the events (point 5) → `200 { "selector", "name", "color", "sync", "shared" }` + pushes to the frontend and the integration |

Account enablement and values are stored per `(service_id, user_id)` variables (the B.15 pattern — no migration).

**6. Milestone 2 — per-user OAuth2 (the Google Calendar / Outlook gate), design only.** Milestone 1 covers every provider whose per-user identity fits `account_schema` fields: CalDAV servers and Nextcloud/Framagenda (app passwords), iCloud (app-specific passwords), token-based APIs, public ICS feeds (no account at all). Google and Microsoft only speak per-user OAuth, which the current `oauth2` machinery (C.1) cannot express — it is admin-scoped and config-level. Sketch, to be detailed when the milestone starts: allow `oauth2` fields in `account_schema`; open the two oauth relay routes (C.5) to the authenticated user when the `key` belongs to the `account_schema` (admin stays required for `config_schema` keys); the WS relays `oauth.get-authorize-url`/`oauth.callback` gain a `user: { "selector" }` field; per-user token storage via a per-user variant of the free config storage (`POST /api/integration/v1/calendar/account/config { "user", "config" }` — keys outside the schema, never shown in the UI, returned by `GET /calendar/account`); a per-user connection state surfaces in the "My calendars" block. Nothing in milestone 1 closes these doors: account payloads already carry the user selector, `(service_id, user_id)` storage exists, and the oauth relay machinery is user-agnostic except for its route guard. Implement it from this sketch, not from scratch.

**Frontend**: the catalog does not key its shelves on the manifest `type` (browse categories, `integration-catalog-categories.md`): a `type: "calendar"` integration is listed under the `categories` of its store index entry (its manifest field, else the indexer's fallback mapping — the `services` shelf, where the native CalDAV entry of `front/src/config/integrations/calendars.json` lives), with the external badge and status like everywhere; `type` stays the technical key of the role rule (non-admin visibility above) and of the screens. Front changes — every device-screen gate, not only the page chrome: `'calendar'` joins the shared `TYPES_WITHOUT_DEVICE_SCREENS` list (`front/src/routes/integration/all/external-integration/utils.js`), which drives the tabs of `ExternalIntegrationPage`, `getInstalledUrl` and the card `type` of the catalog, the post-install redirect of the install page and the `discover-page`/`device-page` guards (redirect to the Configuration screen when reached by URL); the non-admin installed filter of the catalog lets `communication` and `calendar` through. The install screen shows a calendar information line (the privacy sentence of point 5). The generic page gains the "My calendars" block (point 2); the calendar view gains the `calendar.updated` listener (point 1) — no other view change: pushed calendars render exactly like CalDAV ones.

**7. Contracts owned by this file** (the shared `contracts/` tables carry the v1 core surface only — see `contracts/conventions.md`; the manifest field of point 2, the host API endpoints of point 3 and the management routes above complete this list).

*WebSocket messages* (C.4 envelope and conventions):

| Direction | `type` | `payload` |
|---|---|---|
| core → integration | `external-integration.calendar.account-updated` | `{ "user": "<user_selector>" }` — a user enabled or disabled the integration, changed their account values, or toggled a calendar's `sync`/`shared`; no `message_id`, no ack (the `config-updated` family), emitted **after** the core applied the change (on a disable, the user's calendars are already destroyed); the integration re-reads `GET /calendar/account` and `GET /calendar` and adjusts its sync loops |
| core → frontend | `calendar.updated` | `{ "calendar_selectors": [...] }` — on the existing user WS, pushed after any calendar/event write batch, each calendar to its own audience (a shared calendar to every connected user, a private one to its owner; union of previous and new visibility on a transition, point 5) — so the calendar view refetches its displayed range; deliberately in the core `calendar` namespace, not `external-integration.*`: it belongs to the core calendar domain and the internal CalDAV service can adopt it too |

The C.4 **resync contract** extends to the calendar surface: on every (re)connection, a calendar integration additionally re-reads `GET /calendar/account` + `GET /calendar` (core→integration messages emitted during a disconnection are lost, `account-updated` included).

*JS SDK surface* (C.8, `@gladysassistant/integration-sdk`, "calendar" type only):

| Method / handler | Contract |
|---|---|
| `onCalendarAccountUpdated(cb)` | `(userSelector) => Promise` — a user enabled/disabled the integration or changed their account values or toggles; re-read `getCalendarAccounts()`/`getCalendars()` and adjust the sync loops (no ack — fire-and-forget) |
| `getCalendarAccounts()` | `GET /calendar/account` — the users who enabled the integration, with their account values (secrets included) |
| `getCalendars(userSelector?)` | `GET /calendar` — the integration's calendars with their `sync` state; every user's when `userSelector` is omitted (the startup resync) |
| `publishCalendars(userSelector, calendars)` | `POST /calendar` — upsert by `external_id` (≤ 50 per user, point 3) |
| `deleteCalendar(externalId)` | `DELETE /calendar?external_id=...` — destroys the calendar and its events (provider-side deletion) |
| `publishCalendarEvents(calendarExternalId, events, window?)` | `POST /calendar/event` — upsert by `external_id` (≤ 500 per call); `window: { from, to }` additionally prunes the integration's events absent from the list (point 5; manual events never pruned) |

**Verification (manual e2e, environment with the Docker socket)**: dev-install a `type: "calendar"` manifest (a public ICS feed without `account_schema`, then a CalDAV one with `server_url`/`app_password`) → the install screen shows the calendar information line → the integration page shows Configuration / Supervision / Logs and no Devices / Discovery screen → as a non-admin, the installed integration is in the catalog and its page shows only "My calendars" → Enable: the integration receives `calendar.account-updated`, pushes its calendars and a window of events, and they appear in the calendar view **without a reload** → toggle `shared`: the calendar reaches the other users' views and a `calendar.event-is-coming` scene on it fires → toggle `sync` off: its events disappear and the next push answers `403` → Disable: the user's calendars are gone, the other users' untouched → uninstall as admin: every calendar of the integration is gone.

**What v1 anticipated (and it holds)**: extensible manifest `type` + catalog filter, WS `<domain>.<action>` convention, per-user `(service_id, user_id)` variables and per-user blocks (B.15), server-side-enforced authorization gates, the normalize-and-bound doctrine (B.18).
