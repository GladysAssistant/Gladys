# "TTS provider" type: pluggable text-to-speech (implemented)

Goal: that text-to-speech stops being hardwired to Gladys Plus — a self-hosted engine (Piper-like), a cloud TTS API, or any community engine becomes an ordinary external integration of **type `tts`**, selectable as *the* voice of the instance (community request, topic 10422).

This file has no historic section identifier (the README's rule: none is allocated to a new file) — it is cited by its path, `capabilities/tts-type.md`.

**State before this workstream (verified in the code at the time)** — two consumers, both of which called the Gladys Plus gateway **by name**, and both needing a **URL that a player fetches itself**:

- the `MUSIC.PLAY_NOTIFICATION` scene action (`scene.actions.js`): text → `gateway.getTTSApiUrl({ text })` → signed public URL → `device.setValue(device, playNotificationFeature, url, { volume })` — the speaker (Sonos `PlayNotification({ trackUri })`, Google Cast, AirPlay) downloads the URL on its own;
- the voice assistant reply (`gateway.processVoiceMessage.js`): the answer text → same call → `ttsUrl` played by the browser (`Audio.src = ttsUrl`, absolute URL, no base prefixing).

Both consumers now go through `gladys.tts.getSpeechUrl` (point 1); `gateway.getTTSApiUrl` remains as the Gladys Plus transport behind the dispatcher (and behind the untouched `POST /api/v1/gateway/tts` endpoint).

**Why a type and not a capability field.** `capabilities/provider-type.md` sets the bar for a new `type`: *a generic pivot interface the core itself consumes (dashboard, assistant, scenes), never a domain* — anything else is a capability field usable by every type. TTS passes it the way `weather` did: the pivot is the provider interface `tts.synthesize({ text, language })` → audio bytes, consumed by the core alone through the scene engine and the voice assistant — the integration never decides what is spoken, where, nor when. The type also carries what a field could not: the exclusive, instance-wide **active provider** choice (one voice at a time, like the timezone), and a screen set without Devices/Discovery. A TTS integration may still declare capability fields on top (a widget, a scene action), like any type.

## 1. Core refactor (the `forwardToChannels` pattern of B.15, transposed)

A new core manager **`gladys.tts`** (`server/lib/tts/`) decouples consumers from providers.

- **Provider interface**: any stateManager service exposing **`tts.synthesize({ text, language })`** is a TTS provider — the core knows no provider by name; an internal service could implement it tomorrow the same way. **Gladys Plus stays the built-in provider** under the reserved id **`gladys-plus`** (dispatch to the untouched `gateway.getTTSApiUrl`, signed public URL — keeps working through remote access).
- **Active provider**: system variable **`TTS_ACTIVE_PROVIDER`** (default and fallback value `gladys-plus`; otherwise a service selector). One active provider for the whole instance — the TTS voice is an instance-level choice, like the timezone. Admin UI: a "Voice (text-to-speech provider)" card on the **"Artificial Intelligence" integration page** (`front/src/routes/integration/all/openai/`, next to the other voice/chat features rather than in the generic System settings; rendered for admins only, the server enforcing the same rule on the write), fed by `GET /api/v1/tts/provider` (authenticated, non-admin allowed: the frontend also uses it to stop showing the Gladys Plus upsell on the scene action when another provider is active; each provider carries a display `name` — the integration's manifest name — so the select never shows a raw selector) and saved via `POST /api/v1/tts/provider { provider }` (admin, `422` if the value is neither `gladys-plus` nor a service currently exposing `tts.synthesize`). The select commits the selection only once the server accepted it, and reloads the configuration on failure. Each integration provider also carries its `selector` and its service `status`, and the card **says when the selected voice cannot speak** instead of leaving the failure to the server log: Gladys Plus selected while the instance is not connected to Gladys Plus (the default state of a fresh instance — the warning links to the Gladys Plus settings rather than pointing "above", since the Plus card of the page is hidden while an external AI provider is active, `capabilities/ai-type.md`), an integration provider that is not `RUNNING`/`DEGRADED`, a stored selector no server-side provider matches any more; when only Gladys Plus is listed, a hint points at the voice-assistant shelf of the catalog. The Configuration screen of a `tts` integration shows whether it is the active voice (as a warning when it is the active voice but not `RUNNING`/`DEGRADED`: being selected while stopped is a failure state, not a success) and links to the setting, and the install screen's information line links to the Artificial Intelligence page.
- **Consumers** call **`gladys.tts.getSpeechUrl({ text, language })`** → `{ url, provider }` (`language` best effort: the user's for the voice assistant; a scene announcement has no user behind it, so the dispatcher falls back to the **first administrator's language** — the one the instance was set up in — and `null` only when there is no administrator yet, so a provider offering an "automatic" voice never silently speaks its own default language on announcements). `gladys-plus` → the gateway's signed URL, unchanged behavior including the 403 (no Plus) and 429 paths that feed the existing upsell. Integration provider → the proxy service's `tts.synthesize` (WS relay, point 2) returns the audio bytes; the core keeps them **in RAM** (10 min TTL, 32-byte random token — the discovered-devices doctrine: no table, nothing on disk; expired clips are purged lazily on every mint and read, and the cache holds at most **20 clips**, the oldest evicted first — a speaker fetches its URL within seconds, so an evicted clip is one nobody is still playing) and returns `http://<LAN IPv4 of the host>:<SERVER_PORT>/api/v1/tts/audio/<token>.<ext>`. The address is the one the System settings page already advertises (`system.getLocalIp`, the single LAN-address implementation of the core: Docker bridges and virtual interfaces are never candidates, a VPN address is a last resort, a wired RFC1918 address wins, and the numeric `family: 4` some Node versions report is accepted), the port the same `getServerPort()` resolution as `server/index.js`; `localhost` when no LAN address exists (best effort on multi-homed hosts). Behind a Docker bridge (`system.isOnHostNetwork()` false) the only address is the container's, which no speaker can reach: the URL is still minted — there is nothing better to advertise — and a warning is logged pointing at host network mode or the Gladys Plus provider.
- **Defense in depth**: the audio payload is validated **twice** before a byte is cached or put in a URL — by the external-integration proxy (point 2) and again by `getSpeechUrl` itself (buffer type and size bound, content type looked up as an own key of the curated list, extension matching that content type), whatever service implements the provider interface.
- **`GET /api/v1/tts/audio/:token`** is **unauthenticated by design**: a Sonos cannot send a JWT — the high-entropy token is the secret, exactly the trust model of the signed Gladys Plus URL (public URL, capability in the path), scoped to a single short-lived audio. Unknown or expired token → `404`. The route serves the clip with its curated content type; the extension kept in the URL lets players sniff the format.
- **Accepted limitation, documented**: with an integration provider the URL is a **LAN** `http://` URL, minted for speakers. The **voice assistant reply stays text-only with an integration provider**: the browser microphone needs a secure context, so the assistant only runs over HTTPS (Gladys Plus remote access, the mobile app, a reverse proxy) or on `localhost`, and an `http://<LAN IP>` audio source in an HTTPS page is mixed content the browser blocks — the `ttsUrl` is returned but `playTts` fails silently and the user reads the answer. Only on `localhost` (the dev setup) does the voice play. Choose the `gladys-plus` provider for the voice assistant; see the inline-clip lead below. No relaying of local audio through the gateway in v1.
- A configured provider that is stopped or disconnected → `getSpeechUrl` **throws**: a silent fallback to another voice would be a surprise, not a service. What each consumer does with that failure differs, because what they can still deliver differs:
  - **Gladys Plus `402` / `403` / `429`** (payment required, no subscription, quota reached) are **never swallowed**, on either consumer: they are the existing upsell paths (B.13) and keep surfacing as the `payment_required` / `forbidden` / `too_many_requests` voice-assistant errors and as the scene error. The exception is keyed on the **active provider** (`gladys.tts.getActiveProvider()`), not on the status code alone: only Gladys Plus has an upsell, so the same codes thrown by an integration provider mean nothing to the user and degrade like any other failure.
  - **Any other TTS failure on the voice-assistant path** (`gateway.processVoiceMessage`) **degrades to a text-only reply**: the transcription and the answer are already computed and already emitted over the websocket — discarding them behind a generic error would lose a usable answer to a missing voice. The response carries `ttsUrl: null` and the failure is logged.
  - **The `MUSIC.PLAY_NOTIFICATION` scene action still throws**: there is no URL to hand to the speaker, so there is nothing to degrade to. The scene framework (`scene.executeActions.js`) already contains and logs the failure, and the scene continues.
- **Uninstalling the selected provider clears `TTS_ACTIVE_PROVIDER`** (back to the Gladys Plus default): that is not a mid-flight voice swap — it restores the default when the choice no longer exists, instead of leaving a dangling selector that fails every announcement until an admin notices. Documented on the `DELETE .../:selector` row of `contracts/management-api.md`.

## 2. On the integration side — the thinnest possible contract

- **Manifest (C.1)**: `type: "tts"`, nothing else specific — voice, model, speed, per-language voices… all belong to the integration's own `config_schema` (generated form), where the choices are engine-specific by nature. The type-restricted fields of the other types (`messaging`, `contact_schema`, `account_schema`, the `provider` capability requirement) keep their rules: a `tts` manifest declaring them is rejected like any other non-matching type. Same screens as a communication integration: **Configuration only** (no Devices/Discovery — `tts` joins the shared `TYPES_WITHOUT_DEVICE_SCREENS` list of the frontend), technical type `tts`; the install screen shows a dedicated information line (the voice is selected from the Artificial Intelligence page, announcements are served on the LAN); nothing is exposed to non-admins — the catalog hides the type from them like `device`, `weather` and `provider` (installing and choosing the voice are admin acts, a TTS provider has no per-user block). A store TTS manifest declares **`categories: ["assistants"]`** (vocabulary of `integration-catalog-categories.md` §3) — the whole type belongs on the "Voice assistants & AI" shelf, and an undeclared provider would sit in the uncategorized `All`/search-only bucket; the legacy `/dashboard/integration/tts` path redirects to that shelf (§5 of the same spec).
- **Proxy service**: exposes `tts.synthesize({ text, language })` → `{ buffer, contentType, extension }`, the duck-typed interface `gladys.tts` enumerates (`GET /api/v1/tts/provider` lists every service exposing it, Gladys Plus first).
- **WS command (C.4)** `external-integration.tts.synthesize` `{ "message_id", "text", "language" }` (`language` is the requesting user's language or `null`) → `command-result` with `data: { "audio": "<content_type>;base64,..." }` — the camera convention, **without** the `data:` scheme; a standard data URI with its `data:` prefix is accepted too, so an integration using a stock encoder does not fail on an opaque error. The base64 payload is a single line of the standard alphabet: MIME-style line breaks are rejected (`Buffer.from` would silently skip them). Ack within **30 s** (local synthesis on a Pi is slow — a documented exception to the 5 s rule, alongside `camera.get-image`, `weather.get` and `action.run`). Accepted content types: `audio/mpeg`, `audio/wav`, `audio/ogg`, `audio/aac` (what Sonos/Cast/browsers actually play; the URL extension — `mp3`, `wav`, `ogg`, `aac` — is derived from it); decoded audio ≤ **5 MB**, and the data-URI string is bounded **before** it is decoded (the `normalizeWeatherImage` rule: a payload from unaudited code never allocates past the cap); `text` capped at **2000 characters** by the core before relay (truncation, not an error: a long AI answer must still speak its beginning rather than fail). Missing, malformed (characters outside the base64 alphabet — `Buffer.from` would silently skip them and decode a partial clip), oversized or empty audio, or a content type outside the list (looked up as an own key — `constructor` and the other inherited object properties are rejected) → the command fails like a timeout (`ExternalIntegrationUnavailableError`). Constants: `TTS_SYNTHESIZE_TIMEOUT_MS`, `MAX_TTS_AUDIO_SIZE_BYTES`, `MAX_TTS_TEXT_LENGTH`, `TTS_AUDIO_CONTENT_TYPES` in `server/lib/external-integration/constants.js`; `WEBSOCKET_MESSAGE_TYPES.EXTERNAL_INTEGRATION.TTS_SYNTHESIZE` and `SYSTEM_VARIABLE_NAMES.TTS_ACTIVE_PROVIDER` in `server/utils/constants.js`.
- **SDK (C.8)**: `onTtsSynthesize(cb)` — `(text, language) => Promise<string>` resolving the audio data-URI (`audio/mpeg;base64,...`, ≤ 5 MB decoded); it goes into `data.audio` (30 s ack delay).

## 3. Risk assessment

Nothing beyond the standard sandbox — the command is outbound-only (the integration never pushes audio uninvited), the core validates type and size before serving a byte, the audio route exposes exactly one synthesized clip per token and expires, and the RAM cache is bounded by construction (≤ 5 MB per clip, 10 minutes of life, at most 20 clips — ≤ 100 MB worst case). The spoken **text** does transit through third-party code: same trust level as a `message.send` on a communication channel, covered by the existing install warning.

## Tests

- **Manifest** (`validateManifest`): `type: "tts"` accepted; `messaging` / `contact_schema` still rejected outside communication; the vendored `manifest.schema.json` carries the enum value.
- **Proxy** (`registerProxyService`): the `tts` capability only on `type: "tts"` integrations; `tts.synthesize` relay (audio in `command-result.data`, **30 s** timeout honored, `language` defaulted to `null`, every accepted content type mapped to its extension, 2000-character text cap, optional `data:` scheme accepted, missing audio / non-data-URI / unknown or inherited content type / empty or oversized audio / malformed base64 / oversized data-URI string refused before any decode → `ExternalIntegrationUnavailableError`).
- **Manager** (`server/test/lib/tts/`): provider enumeration (Gladys Plus always first, only callable `tts.synthesize` counts), active provider (stored value, Gladys Plus default), default language (first administrator, `null` without one), configuration with display names, selectors and statuses (manifest name, raw selector fallback, stopped provider exposed), `setActiveProvider` (`422` on an unknown provider, nothing written), `getSpeechUrl` (Gladys Plus dispatch with and without URL, LAN URL minting and clip retrieval behind the token, `language` defaulted to `null`, every invalid payload refused before anything is cached, uninstalled / capability-less / non-callable provider → throw, no silent fallback), `getAudio` and `purgeExpiredAudios` (live, unknown and expired tokens, oldest clips evicted beyond the entry cap), `getLocalApiBaseUrl` (SERVER_PORT, numeric `family: 4` accepted, Docker bridges never candidates, physical NIC over tunnels, `localhost` fallback, warning behind a Docker bridge).
- **Consumers**: `gateway.processVoiceMessage` (dispatch with the user's language; text-only degrade with no error event; `Error402` / `Error403` / `Error429` still emit the upsell error and rethrow when Gladys Plus is the active provider, and degrade to text-only when an integration provider throws them), the `PLAY_NOTIFICATION` scene action through `tts.getSpeechUrl`.
- **Controller** (`server/test/controllers/tts/`): `GET /api/v1/tts/provider` (default configuration, non-admin read), `POST /api/v1/tts/provider` (saved, `422` on an unavailable provider, `403` for a non-admin), `GET /api/v1/tts/audio/:token` (200 unauthenticated with the curated content type, 404 on unknown or expired token).
- **Uninstall**: uninstalling the selected provider clears `TTS_ACTIVE_PROVIDER`; uninstalling another integration leaves it untouched.

## Verification (manual e2e, environment with the Docker socket)

Dev-install a `type: "tts"` manifest → the install screen shows the TTS information line → the integration page shows Configuration / Supervision / Logs and no Devices / Discovery screen → the "Voice" card of the Artificial Intelligence page lists Gladys Plus and the integration under its manifest name → select the integration → a scene with a "Play a notification" action speaks on a LAN speaker through `http://<LAN IP>:<port>/api/v1/tts/audio/<token>.mp3`, and the Gladys Plus upsell disappears from the action editor → the voice assistant answers in text only (its `http://` clip is mixed content in the HTTPS page the microphone requires; it plays on `localhost` only) → stop the integration: the scene action fails visibly (scene log) and the Voice card warns that the selected provider is not running → uninstall the integration: the voice card is back on Gladys Plus with no manual reset.

## Later leads

- **Inline clip for the voice assistant**: for that consumer only, return the audio as a `data:<content type>;base64,...` URI instead of the LAN URL — `playSpeechTtsUrl` already does `audio.src = ttsUrl`, so it would play over HTTP, HTTPS and through Gladys Plus remote access alike; the response size the Gladys Plus relay accepts has to be checked first (a 5 MB clip is ~6.7 MB of base64).
- Relaying a local clip through the Gladys Plus gateway so a remote-access browser can play an integration's voice.
- A per-user or per-speaker voice (the manifest and the WS contract already carry `language`; the active-provider choice would become a map).
- Non-MP3 clips on real hardware: `google-cast` hardcodes `contentType: 'audio/mp3'` when it plays a URL, while the contract accepts `wav`, `ogg` and `aac`; Cast and Sonos should be checked with a non-MP3 provider, and the Cast service could derive the content type from the URL extension.
